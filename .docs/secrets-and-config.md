# Секреты и конфиг: как это устроено и что это не защищает

Дорожка SECRETS, 2026-11-06, правки по ревью — тот же день. Код: `src/secrets/`, `src/config/`,
`src/cli/{secrets,doctor,trust}.rs`, `src/commands/defs/{secrets,doctor}.rs`. Пример конфига: `config.example.toml`.

Главный принцип: при любом сомнении ничего не удаляем и не затираем. Запись в хранилище удаляет только человек
(`secrets rm`, `/secrets rm`, `/wipe`); устаревшая запись вреда не несёт.

## Где что лежит

| Что | Где |
|---|---|
| Открытый конфиг, общий слой | `~/.pooprusteek/config.toml` |
| Проектный слой (необязательный) | `.pooprusteek/config.toml`; ищется вверх от папки запуска до корня git, вне git — только папка запуска |
| Файл из `--config` | заменяет оба слоя, запись идёт только в него |
| Данные и кэш | `dirs::data_local_dir()/pooprusteek` (на Windows `%LOCALAPPDATA%`, не roaming) |
| Секреты | системное хранилище (Credential Manager, Keychain, Secret Service), служба `pooprusteek` |
| Копия перед первой правкой | `config.toml.pre-gateway` рядом с конфигом |

## Перенос со старых мест

**Данные** (`dirs::data_dir()/pooprusteek` → новая папка) копируются по явному списку: `history.json`,
`whitelist.json`, `checkpoints.jsonl`, `checkpoints-undone.jsonl`, `mcp.json` и папки `sessions/`, `checkpoints/`,
`tool-output/`, `exports/`, `skills/`. Всё остальное остаётся в старой папке нетронутым: на Windows и macOS старый
конфиг лежит прямо в ней, и «скопировать всё, кроме» унесло бы открытые ключи. Конфиг и его копии не копируются
никогда (они едут отдельным шагом, см. ниже), список оставленного показывается в заметке при запуске. Модель,
семантический индекс, `provider_models.json` и журналы не переносятся (перекачиваются и пересоздаются). `mcp.json`
переносится, потому что без него пропадут серверы MCP; его `env`/`headers` закрыты от модели так же, как конфиг.

Если файл есть в обеих папках и различается, в работе остаётся тот, что свежее по времени изменения, а проигравший
лежит рядом как `имя.legacy` (`.legacy.2`, …). Такая же копия уже лежит — новая не создаётся, повторный запуск ничего
не плодит. Метка `.migrated-from-legacy` ставится только после полного успеха; до этого работаем со старой папкой.
Старая папка не удаляется никогда; записи старого бинаря, сделанные после метки, в новую папку не попадают.

**Конфиг** (`dirs::config_dir()/pooprusteek/config.toml` → `~/.pooprusteek/config.toml`) копируется, пока нового нет.
Старый файл **остаётся на месте ради отката**: старый бинарь читает именно его. Когда ключи подтверждённо лежат в
хранилище (для каждого есть ссылка в новом файле и хранилище отдаёт то же значение), в старом файле значения секретов
заменяются пустыми через `toml_edit`: токены — пустой строкой, ключи записей `[[providers]]` убираются. Все настройки
(тема, провайдеры, `[server]`, `[context]`, комментарии) остаются. Старый бинарь после отката увидит настройки и
попросит токен заново; токен в хранилище ему недоступен. Открытых ключей не остаётся ни в старом файле, ни в
`config.toml.pre-gateway` (его значения затираются после запуска, где все ссылки читаются). Любое сомнение (хранилище
не подтверждает значение, новый файл не читается) — старый файл не трогается.

## Ссылки на секреты

`keyring:global/имя`, `env:ИМЯ`, `cmd:["op","read","…"]`, `file:/путь`, `none`. Любая другая строка в поле
секрета — ошибка загрузки, а не «просто строка». Значение читается при сборке адаптера (`SecretResolver`),
а старые поля (`provider.token`, `providers[].api_key`, `server.api_key`) разворачиваются в память при загрузке,
чтобы остальной код не менялся; в файл они не возвращаются — сохранение пишет только разницу.

`SecretResolver::resolve` блокирует (хранилище, `cmd:`, файл): его зовут с `spawn_blocking`, не с цикла событий.

## Миграция открытых ключей

При запуске (не в изолированном прогоне): ключ записывается в хранилище, читается обратно, сравнивается, и только
тогда в файле на его месте появляется ссылка. Любой сбой оставляет ключ в файле и повторяется при следующем
запуске. Хранилище недоступно (Docker, CI, сервер) — ничего не меняется, в `doctor` видно причину. Перед первой
правкой делается копия `config.toml.pre-gateway`. Одновременно `[[providers]]` зеркалятся в `[[accounts]]`
(`GatewayConfig::from_legacy`), `[gateway] schema = 1`, `enabled = false`.

Длинное значение режется на куски по 900 байт (предел Windows — 2560 байт, пароль там в UTF-16). Перезапись идёт в
новое поколение кусков, заголовок переключается последним, потом старое поколение удаляется: падение на любом шаге
оставляет читаемым либо старое значение целиком, либо новое, но не смесь. `delete` подметает куски прошлого, текущего и
следующего поколений.

## Ключ не прочитался — это не «ключа нет»

Если ссылка есть, а значение не прочиталось (хранилище не ответило, запись повреждена, ссылку не разрешили), токен в
памяти пуст, но приложение **не открывает онбординг** и объясняет причину в чате и строке состояния. Ссылка в файле не
затирается: сохранение, которое её убрало бы, отказывает, пока она не читается. Нет самой записи (хранилище отвечает,
записи нет) — это обычный первый вход. Одна повреждённая запись не делает недоступным всё хранилище.

Конфиг, который не загрузился (ошибка чтения, `schema` новее нашей), помечается «только чтение»: приложение работает на
встроенных значениях (при новой схеме читает понятное, шлюз не включает), а любое сохранение отказывает с понятным
сообщением. Файл, правленный руками и испорченный, не перезаписывается никогда.

## Проектный слой: безобидное сразу, куда уходят запросы — после подтверждения

Проектный слой переопределяет общий по ключам; `[[accounts]]` и `[[routes]]` сливаются по `id`. Он недоверенный.

1. **Запрещено — слой не применяется целиком**, причина в `doctor` и в заметке при запуске: `[server]`, `[update]`,
   `[instructions]`, `[[providers]]`, `active_provider`, `[secrets]`, `[trust]`, `provider.{token,base_url,kind,
   client_version}`, `skills.paths`, у аккаунтов — `api_key`, `direct_token`, `home`, `secret` вида `cmd:`/`file:`/литерал,
   смена `base_url`/`provider` у аккаунта с известным общим `id`, любое значение, похожее на ключ.
2. **Ждёт подтверждения** (fail closed): `[gateway]`, `[[accounts]]`, `[[routes]]`, `[roles]`, то есть всё, что меняет,
   куда уходит запрос. Пока человек не подтвердил именно этот файл, действуют общие значения, а остальное из проекта
   (тема, лимиты агента и т. п.) применяется. `doctor` и заметка при запуске называют, что заблокировано: адреса
   аккаунтов, источник ключа, маршруты, роли, включение шлюза.
3. **Подтверждение**: `pooprusteek trust` показывает то же и записывает в общий конфиг `[trust.projects]` путь и
   SHA-256 содержимого файла. Файл изменился — хэш другой, подтверждение спрашивается заново. `pooprusteek trust
   --revoke` снимает его. Раздел `[trust]` проект менять не может. Диалога в TUI пока нет (GW-TUI).
4. **Ключи отдельно.** Подтверждение не отдаёт ключ: аккаунт из проекта получает секрет только для подтверждённого
   адреса, `pooprusteek secrets bind keyring:global/имя api.example.com` (или `/secrets bind …`). Привязка держится за
   схему: голый `host` значит `https://host`, для http нужно писать `http://host`. Проектный аккаунт без `base_url`
   ключа не получает.

Проектный `.pooprusteek/` закрыт от `write` и `edit` моделью на любой глубине пути, через `..` и через ссылку (она не
спасёт: проверяется и названный путь, и разрешённый). `bash` этого не перекрывает: модель с `bash` может переписать
файл, но хэш изменится, и `pooprusteek trust` спросит снова — подмена не сработает молча.

## Что закрыто (утечки, найденные в карте)

| Канал | Что сделано |
|---|---|
| `history.json` | команды с ключом (`/providers add …`, `/secrets …`, `/mcp add …`) и строки, похожие на ключ, не пишутся; старые записи вычищаются при загрузке |
| Онбординг | токен рисуется точками |
| `debug.log` и трассы | записи журнала отладки (`debug_log`, он же трассы харнесса) идут через `secrets::redact`: известные значения и типичные формы ключей (`sk-`, `ghp_`, JWT, `Bearer …`) вычёркиваются |
| Заголовки DeepSeek | `Authorization`, `Cookie`, `x-api-key` и подобные скрыты целиком, без префикса и хвоста |
| `read_file` | отказывает на файлах секретов и на любом `config.toml` или его копии с открытыми ключами (в том числе забытых в папке данных) |
| `safe_write` | не пускает запись в конфиг (в том числе из `--config`), `.pooprusteek/`, старые папки и файлы `file:` |
| `/wipe` | чистит записи хранилища, токены MCP и файлы конфига (но не `~/.pooprusteek` целиком: там ваши правила); в прогоне с `--config`/`--data-dir` отключён |
| `/logout` | токен убирается из конфига; запись в хранилище остаётся (удаляется `secrets rm`) |
| `--config` | запись идёт в этот файл, а не в настоящий конфиг; хранилище, переносы и настоящие папки не трогаются |
| Редиректы | клиенты провайдеров с ключом в заголовке (`Authorization`, `x-api-key`, `x-goog-api-key`) не следуют редиректам: возвращается понятная ошибка, ключ не уходит. DeepSeek не менялся |
| Права | конфиг, копии, история и журнал отладки пишутся с 0600 на unix; на Windows наследуется ACL профиля |
| Ошибка разбора TOML | печатается только сообщение и позиция, значение — никогда |
| `Debug` | у `Secret`, `ProviderConfig`, `ProviderEntry`, `ServerConfig`, `Account`, `Credential` значения скрыты; `Secret` при освобождении обнуляет свой буфер (копии в заголовках и сокетах этим не достать) |

Не закрыто: `errors.log`, stderr и `tracing` не проходят через `redact` (путей со значением не найдено, но
гарантии нет); MCP stdio пишет сырые строки сервера на уровне `debug` (`RUST_LOG`); сессии, spill инструментов,
семантический индекс и экспорт чата содержат всё, что прочитала модель или вставил пользователь.

## Чего это не защищает — честно

Хранилище и запреты защищают от копии файла, бэкапа, облачной синхронизации, случайного коммита, логов и
случайного чтения через `read_file`. Они **не защищают от процесса того же пользователя**. Агент с `bash`
работает от вашего имени: он может прочитать любой ваш файл, переменные окружения, вызвать `secret-tool`,
`security find-generic-password`, `cmdkey` и добраться до системного хранилища. Разрешая `bash` целиком, вы
разрешаете это. `env:` менее защищено: переменные наследуют все дочерние процессы и на Linux видны в
`/proc/<pid>/environ`. Администратор, вредоносное ПО и дамп памяти тоже вне защиты.

## Команды

- `pooprusteek secrets list | set <имя> | rm <имя> | test | bind <ссылка> <хост>`; значение читается из stdin или
  со скрытого ввода, никогда из аргументов командной строки.
- `/secrets` в TUI то же самое, но `set` принимает значение в строке (строка не пишется в историю; для скрытого
  ввода запускайте CLI). Запись в конфиг применяется при следующем запуске.
- `pooprusteek doctor [--json] [--origins]` и `/doctor`: слои и их статус, откуда каждое значение, какие секреты где
  и разрешаются ли, что заблокировано в проекте, проблемы `GatewayConfig::validate()`, права файлов, http к публичным
  хостам. Значений нет. Код выхода 1, если есть ошибки.
- `pooprusteek trust [--yes] [--revoke]`: подтвердить (или отозвать) проектный конфиг, см. выше.

## Запись конфига

`config::save` не переписывает файл целиком: сравнивает загруженное состояние с текущим и применяет разницу через
`toml_edit`. Комментарии, порядок и незнакомые ключи остаются. Запись идёт под блокировкой `config.toml.lock` с
перечитыванием файла внутри неё, так что два процесса не теряют правки друг друга (замок считается брошенным через
60 с, ожидание 75 с).

В TUI запись не ждёт ни замок, ни диск на цикле событий: `config::save` ставит задание в очередь одного рабочего
потока и возвращается сразу, порядок правок сохраняется, ошибка приходит событием в чат, перед выходом, `/wipe` и
перезагрузкой конфига очередь сбрасывается. В CLI и тестах (очередь не включена) запись идёт на месте. Файл, который
не читается как TOML или как конфиг, не затирается: сохранение отказывает с понятной ошибкой. Правка, которой нет в
этом файле по смыслу (значение из проектного слоя), не теряется молча: снимок её не поглощает.

## Контракты

- `SecretResolver::resolve(&SecretRef, &AccountId) -> Result<Secret, SecretError>`; реализация — `StoreResolver`
  (`Config::secret_resolver()`). Кэш на время процесса: хранилище не опрашивается на каждый запрос.
- `Config` получил `gateway`, `accounts`, `routes`, `roles`, `secrets`, `trust` и служебное `source`. `[[providers]]`
  остаются читаемыми **и пишутся**, пока `/providers` не переведён на аккаунты (GW-TUI): иначе `/providers add`
  терял бы запись.
- `Config::startup_problem()`: конфиг не загружен как есть или токен не прочитался — онбординг не открывать.
- `CommandResult::Detached(Box<dyn FnOnce() -> String + Send>)`: работа вне цикла событий, результат — в чат.
