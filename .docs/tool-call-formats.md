# Разбор вызовов инструментов во всех известных форматах

План от 2026-09-28, прошёл три критики (код и архитектура; безопасность;
полнота форматов). Ход работ — в `.memories/JOURNAL/`, статус шагов — внизу.

## Цель

1. Вызов, записанный моделью в любом известном формате, выполняется.
2. Форматы в одном ответе смешиваются — вызовы выполняются в порядке текста.
3. Нераспознанная разметка вызова не становится молча финальным ответом.
4. Цитата, пример и эхо чужого текста не выполняются.

## Вне объёма

Живые прогоны, харнесс, сценарии на подставном провайдере, правка промпта.
Проверка — `cargo test`, `cargo clippy -D warnings`, `cargo fmt --check`.

## Факты, на которых стоит план

- **Экран собирается из потоковых кусков** (`conversation.rs::append_chunk`),
  итоговый текст `Done` никто не читает (`AgentResult` под
  `allow(dead_code)`), история следующего хода берётся отсюда же
  (`app/mod.rs`). Вырезка в конце хода на экран не влияет. Поток режется на
  первом `<`: форматы на `<` пользователь не видит вовсе — ход молча кончается
  прозой до вызова; форматы без `<` навсегда остались бы в ленте и истории.
- Незнакомый формат: ноль вызовов и ноль ошибок → `finish_or_retry` отдаёт
  `StepEnd::Answer`, модель о неудаче не узнаёт.
- **`task` запускает суб-агента без подтверждения** (`tools_step.rs::spawn_task`),
  суб-агент исполняет shell/write/MCP без человека (`sub_agent.rs`), фоновые
  беседы — `auto_approve: true` (`multichat.rs`).
- `RetryBudget` — один на ход, после удачного шага не сбрасывается, хотя
  комментарий говорит «подряд».
- Промпт сам велит писать `<thinking>…</thinking>` и не звать инструменты
  внутри (`assets/prompts/base.prompt.md`).
- Веб DeepSeek отдаёт формат **V4.1**: vLLM `DSML_TOOL_START =
  "<｜DSML｜ calls>"`, sglang `tool_calls_block_name = " calls"`,
  `strip_string_param_value = False`. «Искажённый DSML» из журнала 2026-09-24 —
  это он, отличие только в удвоенной черте.
- Дыры нынешнего DSML: самозакрытый `invoke …/>` (вызов без аргументов)
  теряется молча; тело `invoke` JSON-ом даёт аргументы `{}`.
- Эталоны: vLLM `ccfd1cea` — 47 парсеров (`vllm/tool_parsers/`, плюс
  `rust_tool_parser` — мост без своего формата); sglang `6aacca2d` — 37
  детекторов (`python/sglang/srt/function_call/`).

## Каталог форматов

У каждого образца в тестах — ссылка на файл эталона.

1. **invoke/parameter** — таблица (приставка × обёртки × кавычки имени × смысл
   `string=`):
   - DSML: V3.2 `function_calls`, V4 `tool_calls` (+ `toolcalls`, `tool`),
     V4.1 ` calls` / ` invoke` / ` parameter` с ведущим пробелом;
     самозакрытый `invoke …/>`; тело JSON-ом (как sglang); нет `string` — как
     `"false"` (как vLLM); незакрытый `parameter` кончается на следующем;
     единственный параметр `arguments`/`input`, которого нет в схеме,
     раскрывается;
   - без приставки (Claude-подобный `<function_calls>`), `｜GCML｜` (GigaChat
     3.5), `steptml:` (внутренность Step3), dots (`<dots_function_call>`, имя без
     кавычек или в `'`), MiniMax M2 (приставка только у обёртки
     `<minimax:tool_call>`).
2. **маркер + JSON** — таблица; конец JSON ищется разбором, а не регуляркой;
   объект или массив; закрывающий маркер необязателен: Hermes/Qwen2.5
   `<tool_call>`, Longcat `<longcat_tool_call>`, Ernie 4.5, Granite 3.0
   `<|tool_call|>`, 3.1 `<tool_call>` без закрытия, 4.0, granite-20b
   `<function_call>` без закрытия и подряд, Llama `<|python_tag|>` (объекты через
   `; `), GigaChat 3 (`<|function_call|>`, `function call<|role_sep|>\n`), Inkling
   (ключ `args`), InternLM, Cohere, Jamba/Hunyuan-A13B `<tool_calls>[…]`, Mistral
   (`[TOOL_CALLS] […]`, `[TOOL_CALLS]x[ARGS]{…}`, `[TOOL_CALLS]x{…}`), Phi-4 mini
   `functools[…]`, Apertus (объект с одним ключом-именем), ответ OpenAI
   `tool_calls` (аргументы строкой).
3. **ключ-значение**: GLM 4.5 (`\n` после имени) / 4.7, Ling3 (буквальный `\\n`,
   вызов без аргументов), Spark, Poolside, Hunyuan / Hy3 / Hy4 (суффиксы тегов
   `<tool_call:opensource>`, `<tool_sep>`; у Hy4 его нет), K2 Horizon `<ifm|…>`
   (необязательный `arg_type`, тело бывает JSON).
4. **function=**: Qwen3-Coder, Seed-OSS `<seed:tool_call>`, MiMo (`html.unescape`),
   Qwen3/Step3.5/Nemotron (`<function=` без обёртки, незакрытый `<parameter=`,
   `<function x>`), MiniCPM5 `<function name=…><param name=…>` (CDATA, сущности XML).
5. **спецтокены**: DeepSeek V3/R1 (`function<｜tool▁sep｜>имя\n```json…```), V3.1
   (`имя<｜tool▁sep｜>{…}`), Step3 (`<｜tool_calls_begin｜>` снаружи, внутри
   `steptml:`), Kimi K2 (`functions.имя:N`; голый счётчик без имени —
   диагностика, имя не угадываем), LFM2 (`<|tool_call_start|>` + pythonic или
   JSON). Выбор после `<｜tool_sep｜>`: `<steptml:invoke` → Step3, `имя\n```json`
   → V3, `{` → V3.1.
6. **отдельные грамматики**: Gemma 4 / FunctionGemma (`call:x{k:<|"|>v<|"|>,…}`,
   `<escape>`), Kimi K3 (`<|open|>call …<|sep|>`, `argument key= type=`,
   `&quot;`), MiniMax M3 (`]<]minimax[>[` перед каждым тегом, теги-имена
   параметров, вложенность, `<item>`), Harmony gpt-oss и Muse Glimmer (вызов
   задаёт получатель `to=functions.x` / `to=<инструмент>`).
7. **pythonic** — подграмматика: сильная внутри маркеров (LFM2, Olmo 3
   `<function_calls>` по вызову на строку, `<|python_start|>`), слабая без них
   (Llama 4 `[f(x=1)]`).
8. **голый JSON** — слабый: xLAM, Llama 3 JSON.
9. **наши**: `<tool_use>` (все нынешние допуски), `[TOOL:…]` (вложенные объекты
   через разбор JSON — закрывает старый BUG).

Терпимость к искажениям веба (`｜`/`|` 1+ раз, `▁` = пробел = `_`, пробел перед
именем тега, суффикс `(:[^>\s]+)?`) задаётся **внутри семейства**, а семейство
выбирается по телу — иначе терпимые маркеры сливают чужие форматы
(`<｜tool▁calls▁begin｜>` V3 и `<｜tool_calls_begin｜>` Step3; `<|tool_call|>`,
`<|tool_call>` и `<tool_call>`).

**Выбор по телу** для общих обёрток (`<tool_call>`, `<tool_calls>`,
`<function_calls>`, `<|tool_call…>`, `<ifm|tool_call>`, `<|tool_call_start|>`):
первый непробельный `{`/`[` → семейство 2 (битый JSON — его диагностика);
`<function[=\s]` → 4; `<invoke` → 1; `идентификатор(` → pythonic (сильный);
`идентификатор` + (`<arg_key>` | `<tool_sep>` | `\n` | закрывающий тег) → 3;
`call:`/`:` → Gemma; иначе — диагностика.

## Доверие

- **Доверенные**: `<tool_use>`, `[TOOL:…]`, DSML V3.2–V4.1, спецтокены DeepSeek
  V3/V3.1. Исполняются как сейчас.
- **Прочие сильные**: в интерактивном ходе — всегда подтверждение, включая
  `task`, `timer`, `todo`; в окне виден формат. При `auto_approve` и в
  суб-агенте — не исполняются, модели уходит просьба повторить в `<tool_use>`.
  Неизвестное имя — проза (семейству 3 нужен `<arg_key>` или имя из каталога).
- **Слабые** (pythonic и JSON без маркера): только если весь ответ без
  рассуждений и пробелов — вызовы, либо единственный блок ```` ```json ```` из
  одних вызовов; имя из каталога; все `required`-поля схемы; не определение
  инструмента (`description` + `parameters.properties`). При `auto_approve` и в
  суб-агенте не исполняются. Не прошло — проза, без диагностики.
- **Эхо**: разметка находки дословно есть в выводе инструмента этого хода — не
  исполняется, диагностика.
- **Переименованный вызов** (имя изменилось при нормализации) — подтверждение
  обязательно, в окне исходное имя.

## Архитектура

```
src/agent/tool_parser/
  mod.rs        вход parse(text, &ParseCtx) -> ParseOutcome; сканер; слияние
  family.rs     struct Family { opener, trust, parse }; таблица семейств
  values.rs     правила значений по семействам, приведение по схеме, имена
  visible.rs    StreamTextTracker и truncate_visible (поток)
  formats/
    tool_use.rs   <tool_use> и [TOOL:…]
    invoke.rs     семейство 1
    json_wrap.rs  семейство 2
    tagged.rs     семейства 3 и 4
    tokens.rs     спецтокены (DeepSeek V3/V3.1, Step3, Kimi K2, LFM2)
    gemma.rs  kimi_k3.rs  minimax_m3.rs  channels.rs (Harmony, Muse)
    weak.rs       pythonic (подграмматика) и голый JSON
```

Каждый файл в `formats/` — своя грамматика; маркеры сканера собираются из
описателей `Family`, отдельной копии нет.

`ParseOutcome { calls, errors, visible }` — `visible` строится тем же проходом,
что и вызовы: вырезка и разбор не расходятся. Аргументы находки хранятся
сырыми (`Json(Value)` или список текстовых параметров с объявленным типом),
приводятся после слияния.

### Сканер (один проход слева направо)

1. Ищется ближайшее из: открывающий маркер семейства, ```` ``` ````, маркер
   рассуждений, встроенный код (пара обратных кавычек в пределах строки).
2. **Рассуждения** (`<thinking>`, `<think>`, позже таблица чужих маркеров): до
   закрывающего тега; незакрытое кончается на первом сильном маркере вызова;
   одинокий закрывающий тег в начале — всё до него рассуждение. Внутри не
   разбирается. Если снаружи вызовов ноль, а внутри есть вызов — диагностика.
3. **Блок ```` ``` ````**: вызовы берутся, только если тело блока — одни вызовы;
   иначе блок — проза.
4. **Встроенный код** — проза.
5. **Маркер семейства**: разборщик возвращает конец и результат. Маркер без
   тела вызова — проза, сканер идёт дальше. Незакрытый маркер с телом вызова —
   ошибка до конца текста: после него ничего не исполняется.
6. Дальше — с конца находки. Внутрь находки сканер не заглядывает: разметка в
   аргументе (`write` документации) — данные.

После прохода: слабые кандидаты (при условии «весь ответ») → нормализация
имён и значений → доверие и эхо → удаление **соседнего** дубля (тот же вызов
после нормализации сразу следом, в другом формате) → вызовы по порядку.

### Значения — таблица по семействам

- Обрезка: V4.1, GLM, Hunyuan, GCML, K3 — как есть; DSML ≤ V4, Qwen3, Seed,
  MiMo — ровно один `\n` с краёв; MiniCPM5, Step3, M3 — полностью (как эталон).
- Раскодирование: `html.unescape` (MiMo), CDATA и сущности (MiniCPM5), `&quot;`
  (K3), `<|"|>` и `<escape>` (Gemma).
- Тип: указанный в самом вызове (`string=`, `type=`, `arg_type`) > схема > нет.
  Из текста в нестроковый тип — только если схема явно нестроковая (с учётом
  `anyOf` и массивов типов). Без схемы — строка (кроме DSML без `string` /
  `string="false"` — попытка JSON, как сейчас). `null` → null только для
  нестрокового типа. Литералы Python — только в pythonic и Llama.
  `NaN`/`Infinity` отвергаются.
- Недобор: неразобранная разметка внутри тела вызова — диагностика.

### Имена

Снимаются `functions.`, `:N`, пространство имён получателя; `mcp__…` не
снимается никогда и по хвосту не сопоставляется. Точное совпадение с
каталогом; затем без учёта регистра и `-`/`_` — только если совпадение
единственное.

### Цикл агента

- `ToolCatalog` — один раз на ход перед циклом (`run_agent_loop`,
  `run_sub_agent`), снимок как в `system_prompt.rs`.
- Ошибки рядом с вызовами: вызовы исполняются, диагностики уходят заметкой с
  ролью system (`### NOTE`) со списком уже выполненных вызовов; бюджет битых
  вызовов не тратится; строка в `StepTrace`.
- Страховка (маркер вызова с именем из каталога не разобрался) — свой бюджет в
  одну попытку; та же разметка после диагностики — проза; текст: «если это
  пример — ответь без изменений».
- `RetryBudget`: счётчик битых вызовов сбрасывается после шага с
  выполненными вызовами.
- Подтверждение по происхождению вызова: `run_generic_tool`, `spawn_task`,
  `timer`, `todo`.

### Показ

- Каждый шаг кончается событием с итоговым видимым текстом; `reduce`
  подменяет им открытое сообщение ассистента. Закрывает MEDIUM «обрезка на
  первом `<`» и LOW «проза после вызова».
- Поток: трекер как есть; одна общая регулярка на маркеры без `<`
  (`[TOOL_CALLS`, `functools[`); ответ, начинающийся с `[`, `{`, ```` ```json ````,
  придерживается.

### Рассуждения DeepSeek (последний шаг)

Поле `reasoning` в `CompletionChunk`; поток DeepSeek отслеживает тип фрагмента
и отдаёт `THINK` туда; `collect_stream` не склеивает его с ответом; мост
`/serve` кладёт в `reasoning_content`. Тесты на составленных событиях —
трасс с `THINK` нет.

## Сознательные отступления от эталонов

- В рассуждениях вызовы не разбираются (Trinity разбирает).
- Имя Kimi K2 по схеме не угадывается.
- DSML без `string` — как vLLM, а не как sglang.
- FunctionGemma: значение в `<escape>` остаётся строкой (vLLM разбирает JSON).
- MiniMax M3: листья значений — строки, без приведения по схеме.
- pythonic: позиционный аргумент — ошибка (эталоны его молча пропускают).
- MiMo разбирается как Qwen3-Coder (срез одного `\n`, терпимость к незакрытому
  `<parameter=`): в тексте их не отличить.
- При сбое разбора sglang откатывает весь ответ в текст; у нас — точечная
  диагностика и повтор.

## Решения по ходу работ

- Таблица семейств живёт в `formats/mod.rs` (`families()`), отдельного
  `family.rs` нет. Вход — `parse_reply(text) -> ParsedReply`, для шага агента
  `parse_step(raw, native)`.
- Обрезка и раскодирование значений — дело грамматики (она знает версию
  формата); `values.rs` только приводит типы по схеме.
- Строки DSML не обрезаются ни в одной версии (как vLLM): шаблон DeepSeek не
  добавляет переводов строк вокруг значения.
- Блок ```` ``` ```` проверяется в два захода: до первой строки ```` ``` ````, а
  если вызов оборвался ровно на ней — сквозным проходом (аргумент DSML-записи
  markdown несёт свои ```` ``` ````). Незакрытый блок с одними вызовами — вызовы;
  незакрытый блок с текстом вокруг вызова — не блок: промпт велит остановиться
  после вызова, и блок часто не закрыт.
- Закрывающий тег значения засчитывается, только если за ним тег того же
  диалекта или конец текста; значение не заходит за следующий открывающий тег
  параметра (как sglang).
- Страховка перенесена в шаг 6: без каталога ей не на что опереться.
- Step3 (снаружи спецтокены, внутри `steptml:invoke`) — не DeepSeek: разбор
  спецтокенов отдаёт тело диалекту `steptml` семейства 1.
- Один маркер у нескольких форматов (`<tool_call>`, `<function_calls>`): сканер
  на позиции пробует все семейства, чей маркер совпал, по очереди; каждое само
  решает, его ли тело. Общего диспетчера по телу нет.
- Приёмка встроена в сканер: находка, от которой после приёмки ничего не
  осталось (чужая разметка с незнакомым именем), для сканера — проза, и
  правила блоков кода работают и для неё.
- Эхо (разметка дословно из вывода инструмента) проверяется только у
  недоверенных форматов: свой `<tool_use>` модель законно повторяет, а
  короткий вызов может совпасть с выводом случайно.
- Страховка срабатывает, только когда имя из каталога стоит внутри тега с
  «вызовным» словом, в значении ключа `name`/`tool`/`function`, сразу за
  спецтокеном или за тегом вызова. Окно «рядом разметка» давало ложные
  тревоги на HTML и `package.json` (в каталоге есть `edit`, `write`, `task`).
- Подтверждение: `ToolApprovalRequest::always_ask` — белый список не действует
  для вызова в чужой разметке или с поправленным именем, в окне сказано почему.
- Рассуждения DeepSeek веба: провайдер копит фрагменты `THINK` и выпускает их
  в `<thinking>…</thinking>` перед первым фрагментом ответа; ответа не было —
  накопленное уходит ответом (как до разделения). Пока копится — пустые куски
  держат таймаут простоя. Внутри рассуждения рвутся `</think` и `<tool_use>`,
  чтобы блок не закрылся раньше и трекер потока мог его заморозить. Формат
  событий восстановлен по коду: трасс с `THINK` нет, живьём не проверено.
- Поток придерживает ответ, начатый с `[` или `{` (может целиком оказаться
  вызовом), и режется на `[TOOL_CALLS`, `functools[`. Код в блоках не
  придерживается: живой поток для ответов с кодом важнее.
