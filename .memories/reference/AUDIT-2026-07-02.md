## CRITICAL

- `[FIXING]` Streaming was never actually live: `DeepseekProvider::complete_stream` drained the whole SSE stream before returning to the caller; the agent runner's 120s idle guard watched an already-full channel; the reqwest client was built with no timeouts at all. `→ src/provider/deepseek.rs` (`new()`, `complete_stream`) + `src/agent/runner.rs` (`run_agent_loop`)
- `[FIXING]` MCP manager mutex held across `call_tool`'s network `.await` while the main event loop takes the *same* mutex on its poll tick → any slow MCP tool call froze the whole TUI, not just the calling turn. `→ src/agent/runner.rs` (tool-call dispatch) + `src/app/mcp_status.rs` (`update_stats`)
- `[FIXING]` GOAL evaluator ran a full LLM completion **inside `handle_event`**, directly on the `select!` loop task → hard UI freeze for the duration of every evaluation call. A parallel event path (`GoalEvaluationDone`) already existed alongside the blocking inline call and had drifted out of sync with it. `→ src/app/goal.rs` (`run_goal_evaluation`) + `src/app/mod.rs` (`handle_event`, `AppEvent::GoalEvaluationDone` arm)
- `[FIXING]` `/goal` was registered **with** a leading slash while dispatch strips the leading slash before matching → the command always resolved to "Unknown command". `→ src/commands/defs/goal.rs` (`Command::name`)
- `[FIXING]` `--acp` mode built a **nested** `tokio::runtime::Runtime` and called `.block_on(...)` from code already running inside `#[tokio::main]` → panics ("Cannot start a runtime from within a runtime") on the first prompt. `→ src/acp/server.rs` (prompt request handler) + `src/main.rs` (`#[tokio::main]`)
- `[FIXING]` Render pipeline re-parsed markdown and re-ran syntect highlighting over the **entire** transcript on every single event (each streamed token, each keystroke, every 120ms tick) with no caching, plus an unbounded internal event queue → monotonic performance degradation that got worse the longer a session ran, up to a streaming "death spiral". `→ src/tui/widgets/chat.rs` (chat render fn) + `src/app/mod.rs` (`AppEvent` channel construction)
- `[FIXING]` MCP stdio transport: piped child stderr was never drained (a chatty server fills the OS pipe buffer at ~64KB and deadlocks), and responses were matched to requests by assuming strict in-order 1:1 delivery with **no JSON-RPC `id` correlation** — one unsolicited server notification desyncs every response after it by one slot. `→ src/mcp/transport.rs` (stdio transport setup, `send_request`)

## MAJOR — `[FIXING]`

- Foreground shell execution had no timeout and no output-size cap — a hung or runaway command blocks the turn forever and unbounded stdout/stderr accumulates in memory. `→ src/tools/shell.rs` (foreground execute path)
- On ru-Windows, PowerShell output in the OEM/cp866 codepage came through as mojibake, and the background reader had no non-UTF8 handling strategy for the first bad line. `→ src/tools/background/spawn.rs` (output reader loop)
- Unix background-process kill targeted a single PID, not the process group → orphaned grandchildren (and the ports they hold) survive a "killed" job. `→ src/tools/background/types.rs` (`force_kill_pid`)
- MCP child processes were never explicitly killed on config reload, server toggle, or app exit — `Transport::close` had **zero call sites** anywhere in the tree; cleanup relied entirely on `kill_on_drop`. `→ src/mcp/transport.rs` (`Transport::close` + impls)
- MCP server initialization ran serially, one server fully awaited before the next started → TUI startup could block up to ~60s per configured server. `→ src/mcp/manager.rs` (`connect_all`/`connect_server`)
- MCP server status stayed "Connected" even after `list_tools` failed for that server — the status field was unconditionally set to Connected regardless of the preceding error. `→ src/mcp/manager.rs` (`connect_server`)
- `persist_config` snapshotted **foreign** servers (discovered from Claude Desktop / VS Code / Cursor configs) into pooprusteek's own `mcp.json`, including their `env` blocks — which may carry secrets belonging to those other tools. `→ src/mcp/config.rs` (`load_mcp_config`, `save_mcp_config`)
- All persistence was non-atomic, truncate-in-place `std::fs::write` — sessions, `config.toml`, `whitelist.json`, `mcp.json` all go through it directly; a crash mid-write corrupts the file. An `atomic_write` helper already existed in `util.rs` but had **zero call sites**. `→ src/util.rs` (`atomic_write`) + `src/config/mod.rs`, `src/mcp/config.rs`, `src/whitelist.rs`, `src/session.rs` (their save fns)
- Tool-approval modal state was a single overwritable slot: a second approval request while one was pending orphaned the first waiter forever (it never resolves); pressing Esc during an open approval cleared the chat instead of aborting/declining the approval.
- Pending tool approvals on a **non-focused** conversation were invisible — nothing surfaced the request until the user happened to focus that chat.
- The background-output overflow flag was sticky — once a job's buffer overflowed once, the flag never cleared even after the buffer had room again.
- `@file` mention line-range expansion could slice out of bounds on user-supplied line numbers exceeding the file's length (or a reversed range). `→ src/cli/file_mentions.rs` (`extract_mentions`)
- The skills frontmatter parser kept only the **first** occurrence of a repeated YAML-ish key, silently dropping the rest. `→ src/skills/` (frontmatter parser)
- Tilde (`~`) expansion was broken two different ways — skills discovery resolved `~/x` to `/x` (dropped the tilde instead of expanding to `$HOME`) on Unix.
- Session file format version was written on save but never checked on load — a future format change would load silently instead of failing loud or migrating.
- `/help` hand-listed 8 of the 31 registered slash commands instead of being generated from the live registry.
- Markdown bold/italic/strikethrough rendered as **plain, unstyled text** — the renderer built a `Span::styled` with an empty string and the modifier attached to nothing, so the style had no visible effect. `→ src/tui/markdown.rs` (inline-tag handling for `Tag::Strong`/`Emphasis`/`Strikethrough`)
- The stats panel re-read and re-parsed the entire session file from disk on **every frame** instead of caching between renders.
- The landing screen re-parsed **all** sessions on disk on every 120ms tick.
- An MCP server name longer than 27 characters crashed the MCP panel via an unguarded `gap - 4` subtraction underflow.
- Scroll row-count estimation diverged from ratatui's actual word-wrap — the streaming tail could be scrolled out of view, and the estimate was roughly 2x off for CJK text.
- Token-count estimation re-scanned all attached files from scratch on every frame instead of once per attachment change.
- The DeepSeek session token was saved world-readable (0644, no explicit permission hardening) and echoed in plaintext to the terminal during onboarding instead of being masked.
- The `gzip` `Accept-Encoding` header was sent without the reqwest `gzip` feature enabled — if the server ever honored it, the response body would be undecoded compressed bytes fed to the SSE parser as text.
- Retry backoff used `2^attempt` with no ceiling — silently overflows at a high attempt count.
- Infinite retry (`max_retries = -1`) had no total-time cap, matching the existing HIGH entry in `BUGS.md`.

## MAJOR — `[OPEN]`

- DeepSeek remote chat sessions are created on every fork/new chat but never deleted — `delete_remote_session` exists and is fully implemented but has **zero call sites** anywhere in the codebase, so the user's DeepSeek account accumulates unbounded junk sessions over time. `→ src/provider/deepseek.rs` (`delete_remote_session`)
- Wire `MCPManager::shutdown_all` (if/when it exists — currently there is no such method; only `tools::background::shutdown_all` is called) into the app exit path so MCP child processes are terminated on quit, not just background shell jobs.
- Foreground child PID tracking is a single **global** slot, not per-conversation — with parallel chats, Esc/Ctrl+C in one conversation can kill a different conversation's running foreground process; this is also an upward `tools` → `app` dependency that the layering invariant forbids. `→ src/app/mod.rs` (`FOREGROUND_CHILD_PID`, `kill_foreground_child`)
- `send_to_agent` takes an input/feedback argument that is **never read** in its body (parameter is prefixed `_input`) — GOAL feedback currently reaches the model only indirectly, via UI notice text appended to history, not through this parameter. `→ src/app/mod.rs` (`send_to_agent`)
- The focused-conversation and background-conversation agent-event reducers duplicate similar logic (empty-message placeholder pop, generation stats, autosave) and have already diverged: the focused path records stats and autosaves, the background path does neither. `→ src/app/mod.rs` (`handle_event`) vs `src/app/multichat.rs` (`handle_background_event`)
- Tool-approval whitelisting is a dual store — an in-memory `approved_tools` set and a persisted whitelist file — that can drift out of sync (approve in-memory without persisting, or edit the file without reloading). `→ src/app/mod.rs` (`approved_tools`) + `src/whitelist.rs`
- Model-visible message history and UI-only/display message content are not cleanly separated — needs an explicit split between what the model sees and what only renders.
- PoW challenge is solved once, before entering the retry loop, so a retry reuses a potentially stale/expired solved challenge instead of re-solving; the solve itself also runs directly on the async task rather than `spawn_blocking`, so it's CPU-bound work competing with the event loop's executor threads. `→ src/provider/pow.rs` + `src/provider/deepseek.rs` (retry loop call sites)
- The outgoing request's `"model"` field is a hardcoded literal `"deepseek-chat"`, ignoring whatever model the user configured. `→ src/provider/deepseek.rs` (request-building fn)
- `max_tools_per_step` truncates the tool-call list with `.take(n)` and silently drops the excess — the dropped calls never get a corresponding `tool_result` message, leaving "phantom" unanswered tool_call references in the conversation history sent back to the model. `→ src/agent/runner.rs` (tool-call dispatch loop)
- `tool_parser`'s stream-visible-text truncates displayed text at the first bare `<`, hiding legitimate text (matches existing MEDIUM entry in `BUGS.md`).
- The legacy `[TOOL:name] {json}` regex uses a non-nesting brace pattern and cannot parse tool arguments containing nested JSON objects. `→ src/agent/tool_parser.rs` (legacy-format regex)
- Fenced code-block examples containing tool-call syntax get parsed and executed as real tool calls during auto-approve (background) turns.
- `SseLineBuffer` has no maximum size and its per-line drain does string slicing/reallocation in a loop, making sustained throughput O(n²) in the accumulated buffer size. `→ src/provider/sse.rs`
- `deepseek.rs` is ~1820 lines covering roughly a dozen responsibilities (auth, ~30 endpoints, session state, prompt building, SSE, retry), and contains a fully dead, self-contained "enhanced" typed SSE parser (`parse_sse_event` building `ParsedSSEEvent`) with no call sites — the actual streaming path uses the separate, simpler `process_stream_line` instead. A split (endpoints/http/session/stream) is planned. `→ src/provider/deepseek.rs` (`parse_sse_event` vs `process_stream_line`), `src/provider/types.rs` (`ParsedSSEEvent`)
- `keys.rs`'s Enter-key handling arm is large (~235 lines) and `CommandResult` has 17 variants — a key→intent and intent→effect decomposition is planned to shrink both.
- Sidechat focused-finish leak: tabbing away into a running `/btw` sidechat and back means its result may never flush into the parent conversation.
- Roughly a dozen dead structs remain in `src/provider/types.rs` with no remaining call sites.
- `AppState`'s error field is written on failure paths but never actually rendered anywhere in the UI.
- `GoalCycleFinished` is a defined `AppEvent` variant with no sender anywhere in the codebase.
- The PoW solver runs a ~26KB wasm binary loaded from `assets/` via `wasmtime` 27 — the binary breaks entirely if `assets/` is missing at runtime; a native SHA-3 reimplementation is planned specifically to drop the `wasmtime` dependency.
- Several dependencies are behind current major/minor releases: `reqwest` 0.12→0.13, `ratatui` 0.29→0.30.2, `crossterm` 0.28→0.29, `pulldown-cmark` 0.12→0.13, `toml` 0.8→1.x, `wasmtime` 27→46.

## ACCEPTED

- `[ACCEPTED]` The DeepSeek web API is reverse-engineered and unofficial — it may change or break at any time, with no SLA.
- `[ACCEPTED]` `bash`/`powershell` tools run arbitrary commands by design, with no sandbox — the trust boundary is the tool-approval modal plus `/whitelist`, not the tool implementation itself.
- `[ACCEPTED]` Client fingerprint headers are internally inconsistent (an Android `x-client-platform` header alongside a desktop browser User-Agent) — revisit only if DeepSeek starts blocking sessions on this basis.
