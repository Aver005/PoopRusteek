## CRITICAL

- `[FIXED]` Streaming was never actually live: `DeepseekProvider::complete_stream` drained the whole SSE stream before returning to the caller; the agent runner's 120s idle guard watched an already-full channel; the reqwest client was built with no timeouts at all. Fixed: `complete_stream` spawned as its own task (`agent/runner.rs`, `agent/sub_agent.rs`) so the idle guard races the live network call; client built with `connect_timeout(10s)` + `read_timeout(120s)`; stray `gzip` `Accept-Encoding` header removed; retry backoff made `saturating`; `SseLineBuffer` rewritten byte-based with a 4MiB cap. `→ src/provider/deepseek.rs` (`new()`, `complete_stream`) + `src/agent/runner.rs` (`run_agent_loop`) + `src/provider/sse.rs`
- `[FIXED]` MCP manager mutex held across `call_tool`'s network `.await` while the main event loop takes the *same* mutex on its poll tick → any slow MCP tool call froze the whole TUI, not just the calling turn. Fixed: lock-free `MCPManager::client_for` handles used by runner/sub_agent for the actual call; `McpStatus::update_stats`/`refresh_view` switched to `try_lock` + changed-flags; `/mcp reload|toggle|reconnect` moved off the event loop via `AppEvent::McpOperationDone`. `→ src/mcp/manager.rs` (`client_for`) + src/app/mcp_status.rs (`update_stats`)
- `[FIXED]` GOAL evaluator ran a full LLM completion **inside `handle_event`**, directly on the `select!` loop task → hard UI freeze for the duration of every evaluation call. A parallel event path (`GoalEvaluationDone`) already existed alongside the blocking inline call and had drifted out of sync with it. Fixed: evaluation now runs via `spawn_goal_evaluation` task → `AppEvent::GoalEvaluationDone(GoalEvalOutcome)`, handled by a single `handle_goal_evaluation_done` path; the dead duplicate inline path and the unused `GoalCycleFinished` variant were deleted; a stale-verdict guard was added. `→ src/app/goal.rs` (`run_goal_evaluation`, `spawn_goal_evaluation`) + `src/app/mod.rs` (`handle_event`, `AppEvent::GoalEvaluationDone` arm)
- `[FIXED]` `/goal` was registered **with** a leading slash while dispatch strips the leading slash before matching → the command always resolved to "Unknown command". Fixed, plus a registry round-trip test added. `→ src/commands/defs/goal.rs` (`Command::name`)
- `[FIXED]` `--acp` mode built a **nested** `tokio::runtime::Runtime` and called `.block_on(...)` from code already running inside `#[tokio::main]` → panics ("Cannot start a runtime from within a runtime") on the first prompt. Fixed with `block_in_place` + `Handle::current()`. `→ src/acp/server.rs` (prompt request handler) + `src/main.rs` (`#[tokio::main]`)
- `[FIXED]` Render pipeline re-parsed markdown and re-ran syntect highlighting over the **entire** transcript on every single event (each streamed token, each keystroke, every 120ms tick) with no caching, plus an unbounded internal event queue → monotonic performance degradation that got worse the longer a session ran, up to a streaming "death spiral". Fixed: `run_loop` now drains up to 256 queued events then renders once behind a dirty flag (`tick_is_visual`, so idle = zero draws); `tui/widgets/chat.rs` gained a per-message thread-local markdown/syntect cache keyed by a content fingerprint with a 4096-entry eviction cap; token-estimate results are cached too. `→ src/tui/widgets/chat.rs` (chat render fn) + `src/app/mod.rs` (`run_loop`)
- `[FIXED]` MCP stdio transport: piped child stderr was never drained (a chatty server fills the OS pipe buffer at ~64KB and deadlocks), and responses were matched to requests by assuming strict in-order 1:1 delivery with **no JSON-RPC `id` correlation** — one unsolicited server notification desyncs every response after it by one slot. Fixed: stderr drained continuously; requests/responses correlated by JSON-RPC `id` (notifications skipped); `Transport::close()` now has real call sites (toggle/remove/reload + app-exit `shutdown_all`) on top of `kill_on_drop`; server connects run concurrently instead of serially; status reporting is honest about failures; `persist_config` only saves servers pooprusteek itself owns (foreign servers get enable/disable overrides only, never a copy of their `env`/secrets). `→ src/mcp/transport.rs` (stdio transport setup, `send_request`, `close`) + `src/mcp/manager.rs` (`connect_all`) + `src/mcp/config.rs` (`persist_config`)

## MAJOR — `[FIXED]`

- Foreground shell execution had no timeout and no output-size cap — a hung or runaway command blocks the turn forever and unbounded stdout/stderr accumulates in memory. `→ src/tools/shell.rs` (foreground execute path)
- On ru-Windows, PowerShell output in the OEM/cp866 codepage came through as mojibake, and the background reader had no non-UTF8 handling strategy for the first bad line. `→ src/tools/background/spawn.rs` (output reader loop)
- Unix background-process kill targeted a single PID, not the process group → orphaned grandchildren (and the ports they hold) survive a "killed" job. `→ src/tools/background/types.rs` (`force_kill_pid`)
- MCP child processes were never explicitly killed on config reload, server toggle, or app exit — `Transport::close` had **zero call sites** anywhere in the tree; cleanup relied entirely on `kill_on_drop`. `→ src/mcp/transport.rs` (`Transport::close` + impls)
- MCP server initialization ran serially, one server fully awaited before the next started → TUI startup could block up to ~60s per configured server. `→ src/mcp/manager.rs` (`connect_all`/`connect_server`)
- MCP server status stayed "Connected" even after `list_tools` failed for that server — the status field was unconditionally set to Connected regardless of the preceding error. `→ src/mcp/manager.rs` (`connect_server`)
- `persist_config` snapshotted **foreign** servers (discovered from Claude Desktop / VS Code / Cursor configs) into pooprusteek's own `mcp.json`, including their `env` blocks — which may carry secrets belonging to those other tools. `→ src/mcp/config.rs` (`load_mcp_config`, `save_mcp_config`)
- All persistence was non-atomic, truncate-in-place `std::fs::write` — sessions, `config.toml`, `whitelist.json`, `mcp.json` all go through it directly; a crash mid-write corrupts the file. An `atomic_write` helper already existed in `util.rs` but had **zero call sites**. `→ src/util.rs` (`atomic_write`) + `src/config/mod.rs`, `src/mcp/config.rs`, `src/whitelist.rs`, `src/session.rs` (their save fns)
- Tool-approval modal state was a single overwritable slot: a second approval request while one was pending orphaned the first waiter forever (it never resolves); pressing Esc during an open approval cleared the chat instead of aborting/declining the approval.
- Pending tool approvals on a **non-focused** conversation were invisible — nothing surfaced the request until the user happened to focus that chat.
- The background-output overflow flag was sticky — once a job's buffer overflowed once, the flag never cleared even after the buffer had room again.
- `@file` mention line-range expansion could slice out of bounds on user-supplied line numbers exceeding the file's length (or a reversed range). `→ src/cli/file_mentions.rs` (`extract_mentions`)
- The skills frontmatter parser kept only the **first** occurrence of a repeated YAML-ish key, silently dropping the rest. `→ src/skills/` (frontmatter parser)
- Tilde (`~`) expansion was broken two different ways — skills discovery resolved `~/x` to `/x` (dropped the tilde instead of expanding to `$HOME`) on Unix.
- Session file format version was written on save but never checked on load — a future format change would load silently instead of failing loud or migrating.
- `/help` hand-listed 8 of the 31 registered slash commands instead of being generated from the live registry.
- Markdown bold/italic/strikethrough rendered as **plain, unstyled text** — the renderer built a `Span::styled` with an empty string and the modifier attached to nothing, so the style had no visible effect. `→ src/tui/markdown.rs` (inline-tag handling for `Tag::Strong`/`Emphasis`/`Strikethrough`)
- The stats panel re-read and re-parsed the entire session file from disk on **every frame** instead of caching between renders.
- The landing screen re-parsed **all** sessions on disk on every 120ms tick.
- An MCP server name longer than 27 characters crashed the MCP panel via an unguarded `gap - 4` subtraction underflow.
- Scroll row-count estimation diverged from ratatui's actual word-wrap — the streaming tail could be scrolled out of view, and the estimate was roughly 2x off for CJK text.
- Token-count estimation re-scanned all attached files from scratch on every frame instead of once per attachment change.
- The DeepSeek session token was saved world-readable (0644, no explicit permission hardening) and echoed in plaintext to the terminal during onboarding instead of being masked.
- The `gzip` `Accept-Encoding` header was sent without the reqwest `gzip` feature enabled — if the server ever honored it, the response body would be undecoded compressed bytes fed to the SSE parser as text.
- Retry backoff used `2^attempt` with no ceiling — silently overflows at a high attempt count.
- Infinite retry (`max_retries = -1`) had no total-time cap, matching the existing HIGH entry in `BUGS.md`.

## MAJOR — `[OPEN]`

- DeepSeek remote chat sessions are created on every fork/new chat but never deleted — `delete_remote_session` still exists and is fully implemented but still has **zero call sites** anywhere in the codebase (verified 2026-07-02 post-refactor), so the user's DeepSeek account accumulates unbounded junk sessions over time. `→ src/provider/deepseek.rs` (`delete_remote_session`)
- Foreground child PID tracking is still a single **global** slot (`AtomicU32`), not per-conversation — with parallel chats, Esc/Ctrl+C in one conversation can kill a different conversation's running foreground process; this is also an upward `tools` → `app` dependency that the layering invariant forbids. Verified still true post-refactor. `→ src/app/mod.rs` (`FOREGROUND_CHILD_PID`) + `src/tools/shell.rs` (writes it)
- Tool-approval whitelisting is a dual store — an in-memory `approved_tools` set and a persisted whitelist file — that can drift out of sync (approve in-memory without persisting, or edit the file without reloading). Partially addressed this session (`whitelist::persist_approval` now makes "always allow" survive restarts) but the dual-store shape itself remains. `→ src/app/mod.rs` (`approved_tools`) + `src/whitelist.rs`
- PoW challenge is solved once, before entering the retry loop, so a retry reuses a potentially stale/expired solved challenge instead of re-solving; the solve itself also runs directly on the async task rather than `spawn_blocking`, so it's CPU-bound work competing with the event loop's executor threads. Verified still true. `→ src/provider/pow.rs` + `src/provider/deepseek.rs` (retry loop call sites)
- The outgoing request's `"model"` field is a hardcoded literal `"deepseek-chat"`, ignoring whatever model the user configured. Verified still true (`src/provider/deepseek.rs:454`). `→ src/provider/deepseek.rs` (request-building fn)
- `tool_parser`'s stream-visible-text still truncates displayed text at the first bare `<`, hiding legitimate text (matches existing MEDIUM entry in `BUGS.md`); the legacy `[TOOL:name] {json}` regex still uses a non-nesting brace pattern and cannot parse nested JSON objects; fenced code-block examples containing tool-call syntax can still be parsed and executed as real tool calls during auto-approve (background) turns. Verified still true. `→ src/agent/tool_parser.rs`
- MCP tool arguments are still passed with **no schema validation**. `→ src/mcp/client.rs`
- Theme is still hardcoded (Catppuccin Mocha); `ui.theme` config is ignored. `→ src/tui/theme.rs`
- `mcp__` still uses `__` as a separator → name collision possible if a server/tool name contains `__`. `→ src/mcp/manager.rs`
- History deduplication still only catches **consecutive** duplicates. `→ src/session.rs`
- `deepseek.rs` is still a large multi-responsibility file (auth, ~30 endpoints, session state, prompt building, SSE, retry) covering roughly a dozen responsibilities. The dead "enhanced" typed SSE parser (`parse_sse_event`/`ParsedSSEEvent`) was removed this session, but the file split itself (endpoints/http/session/stream) is still planned, along with dedup of the ~26 unused `DeepseekProvider` REST wrappers deliberately kept in a separate `#[allow(dead_code)]` impl block pending that split. `→ src/provider/deepseek.rs`
- `keys.rs`'s Enter-key handling arm and `CommandResult`'s variant count remain a planned key→intent / intent→effect decomposition target (unchanged by this session's fixes, which were behavioral, not structural, in that file).
- The PoW solver still runs a ~26KB wasm binary loaded from `assets/` via `wasmtime` 27 — the binary breaks entirely if `assets/` is missing at runtime; a native SHA-3 reimplementation is planned specifically to drop the `wasmtime` dependency.
- Several dependencies are still behind current major/minor releases: `reqwest` 0.12→0.13, `ratatui` 0.29→0.30.2 (note: MSRV/ratatui bumped for the `unstable-rendered-line-info` feature this session, but not to the latest minor), `crossterm` 0.28→0.29, `pulldown-cmark` 0.12→0.13, `toml` 0.8→1.x, `wasmtime` 27→46.
- CI clippy runs advisory (`continue-on-error: true`) rather than blocking — flipping it to blocking is pending until historical warnings are paid down further (they are currently at 0, so this is now mostly a formality, but not yet flipped). `→ .github/workflows/ci.yml`

## ACCEPTED

- `[ACCEPTED]` The DeepSeek web API is reverse-engineered and unofficial — it may change or break at any time, with no SLA.
- `[ACCEPTED]` `bash`/`powershell` tools run arbitrary commands by design, with no sandbox — the trust boundary is the tool-approval modal plus `/whitelist`, not the tool implementation itself.
- `[ACCEPTED]` Client fingerprint headers are internally inconsistent (an Android `x-client-platform` header alongside a desktop browser User-Agent) — revisit only if DeepSeek starts blocking sessions on this basis.
