## Fixed

**#1 (Critical) — `util::atomic_write` could lose data entirely, not just
truncate it.** The `#[cfg(windows)]` block removed the target file before
`rename` on the claim that `std::fs::rename` fails when the target exists on
Windows — false; `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` already
replaces. The remove opened a window where a crash left *no* file at all,
worse than the truncation the function exists to prevent. Also folds in #12
(Medium): `File::sync_all()` before the rename (data ordered ahead of the
rename, no zero-length file on crash) and a unique temp name (pid +
process-wide `AtomicU64`) so two concurrent writers to one path can no longer
share a temp file; best-effort temp cleanup on failure. Three tests, replacing the old combined one (net +2).
`→ src/util.rs` (`atomic_write`)

Consequence: `src/app/persist.rs`'s module doc no longer cites the fixed
`.tmp` path as a reason to serialize writes — only the snapshot-ordering
reason still holds.

**#2 (Critical) — a config.toml missing one section or key failed to parse,
and the TUI silently fell back to full defaults for the whole run.** Only 8
of 12 `Config` sections/fields carried `#[serde(default)]`. Fixed:
`provider`/`ui`/`agent`/`mcp` got `#[serde(default)]` on `Config`, and every
scalar field of `ProviderConfig`/`UiConfig`/`AgentConfig` got
`#[serde(default = "named_fn")]` with a named function per field — not a bare
`#[serde(default)]`, which would have zeroed `max_steps_per_turn`/floored
`auto_compact` to `false` instead of the real defaults (256 / true). The three
structs gained `Default` impls built from those same functions; `Config`
itself now derives `Default` (its hand-written impl is gone). No
`deny_unknown_fields` added — an older config with a stale key must keep
parsing. Four new tests, including a regression for the bare-`default`
zeroing trap. `→ src/config/mod.rs`

**#5 (High) — CORS was wide open regardless of whether auth was configured.**
`Access-Control-Allow-Origin: *` and its two sibling headers went out on every
`/serve` response unconditionally, while the bearer check only engages when
`api_key` is `Some` (default `None`). With no key set, any web page the user
had open could cross-origin `POST /v1/chat/completions` to loopback and read
the reply — driving the user's DeepSeek account and any `[[providers]]` keys.
Fixed: the three headers now go out only when `context.api_key.is_some()`.
One test over a real loopback socket asserting `/health` and the `OPTIONS`
preflight agree, and that headers are absent with no key configured.
`→ src/server/http.rs`

**#11 (Medium) — bare `String::from_utf8_lossy` on child stdout/stderr in the
harness itself**, violating invariant 4 in code that postdates the invariant.
Both call sites replaced with `crate::util::decode_process_output`.
`→ src/harness/scenario.rs`

**#16 (Low) — `sandbox/config.template.toml` advertised three `[ui]` keys
that no longer exist** (`show_status_bar`, `show_line_numbers`,
`max_message_length` — `UiConfig` holds only `theme`/`custom_themes` since the
2026-07-15 sweepables pass). Dropped from the template.
`→ sandbox/config.template.toml`

## Clippy pass — finding #15, and what it turned out to be

`[lints.clippy]` added to `Cargo.toml` with a single lint:
`redundant_clone = "deny"`. Three things the review got wrong here, all found
by running clippy rather than reading it:

- **The `perf` group is already on.** Clippy enables correctness/suspicious/
  style/complexity/perf by default; the group is clean, and
  `large_enum_variant` — which the review asks for by name — lives inside it
  and is silent. There was nothing to add.
- **`needless_collect` was rejected**, not adopted. All three hits are false
  positives on the same shape: `collect()` deliberately ending a borrow before
  a mutation or an `.await`. `mcp/manager.rs` spends six comment lines saying
  exactly that, and clippy's suggested rewrite for
  `background/registry.rs:239` would move `reg.procs = persistent` *ahead of*
  the `drain()` it feeds. The rejection and its reason are in the `Cargo.toml`
  comment so this does not get re-proposed.
- **`warn` would have been decorative.** A specific lint level in `Cargo.toml`
  outranks `-D warnings` — the `[lints.rust]` comment already documents this
  for `linker_messages`. Hence `deny`. Verified by probe: reintroducing one
  clone gives `error: redundant clone`, exit 101; probe removed.

Nine redundant clones removed across `app/keys/mcp.rs` (×2),
`app/keys/onboarding.rs`, `app/providers.rs`, `commands/defs/cwd.rs`,
`commands/defs/import.rs`, `server/openai.rs`, `tools/registry.rs`,
`tui/render/mcp.rs`.

`#[allow]` → `#[expect]`: 10 attributes plus one module-level `#![allow]` in
`provider/types.rs` that the review's grep pattern could not match. One
`allow` survives deliberately (`app/events.rs`: under `cargo test` the fields
count as read, so `expect` would be unfulfilled — the code says so). One was
deleted rather than converted: `app/system_prompt.rs::build` carries
`too_many_arguments` with exactly 7 parameters, and the lint fires above 7 —
a dead attribute, which is precisely the rot `expect` exists to prevent.

Now 1 `allow` and 26 `expect` in the crate.

## Context compaction — step 1 (measurement only, no behaviour change)

Not a review finding; step 1 of the plan decided the same day in
`.docs/context-compaction.md` §7 — closes half of #3 (the dead
`max_context_messages`/`auto_compact` keys), the rest of #3 and #4 wait for
the later rungs.

New `src/context/` module, peer of `semantic/`: `budget.rs` holds
`budget_tokens` (`chars / 3`, deliberately pessimistic — see the plan for
why), `conversation_tokens`, `ContextBudget`, `BudgetSnapshot`,
`WindowSource`. `ContextBudget::usable()` returns `Option<u32>` — `None` for
an unknown window or a reserve that swallows it, so the ladder degrades to
off (invariant 12) instead of acting on a guess. A window set via
`[context] context_window` always outranks whatever the provider reports
(`learn_provider_window`); the status bar marks a hand-set window with `*`.

New `[context]` config section (`auto_compact`, `context_window`,
`reserved_tokens`, `preserve_recent_tokens`, `tool_output_limit`);
`auto_compact` moved out of `[agent]`, and `max_context_messages` deleted
outright (never read anywhere — this closes that half of finding #3).
Measurement point: `run_agent_loop` sends `AppEvent::ContextUsage` right
after `build_step_request` — the one place that sees exactly what goes on
the wire, and it runs on the agent task, not the event loop.
`AppEvent::ContextWindowLearned` is asked once at startup on a spawned task;
`CompatClient::context_window()` reads `context_length` off `GET /models`.
Status bar shows e.g. `ctx:50% of 128k`, and shows nothing when the window
is unknown.

Four findings worth keeping in mind for the next rung:

1. **Real token counts are not available in the agent loop today.** The loop
   streams via `complete_stream`, and `CompletionChunk` carries only
   `content` and `finish_reason` — no `usage`. `request_to_openai` does not
   ask for `stream_options: {include_usage: true}`. So the plan's "count
   tokens from the provider's `prompt_tokens`" idea cannot happen until both
   are added; step 1 ships on the local estimate alone, and the plan's
   calibration step is deferred until then.
2. **`ChatMessage.total_tokens` is not context usage.** It is
   `estimate_tokens` over the assistant's own reply, set in
   `App::record_gen_stats` after a turn, and the status bar's `tot:` figure
   sums those. Easy to mistake for window occupancy — it is not the same
   number as the new `ctx:` figure.
3. **`cargo clippy --bin pooprusteek` (no `--all-targets`) treats test-only
   code as dead**, and CI runs exactly that with `-D warnings`. Consequence:
   a module of "groundwork for the next rung" cannot land — every public item
   needs a live caller in the shipping build. `is_over`, `remaining`,
   `preserve_recent_tokens` (with its `MIN/MAX_PRESERVE_TOKENS`) were
   written, tested, and then removed for this reason; their formulas stay in
   `.docs/context-compaction.md` §4 and return with the rung that uses them.
   Real constraint on how the remaining rungs must be sequenced.
4. **Provider window coverage is partial.** Only `context_length` on
   `GET /models` is read (OpenRouter and gateways that copy it). LM Studio
   and Ollama expose theirs on non-OpenAI routes (`/api/v0/models`,
   `/api/show`) and are not covered yet. DeepSeek web does not report one at
   all.

## Context compaction — step 2 (rung 0: cap tool output at capture)

Step 2 of `.docs/context-compaction.md` §7 — the lowest rung of the ladder:
cut a tool result down before it ever enters history, rather than after.

New `src/context/tool_output.rs`, `cap_tool_output(text, limit_chars)`. It
keeps **both ends** — 20% head, 80% tail — with a marker between them naming
how many chars were cut and stating that the tool ran and only the text was
trimmed. The tail gets the larger share because exit status, error text and
the summary line live there; this follows Roo's `truncateOutput`, which
splits 20/80 for the same reason. Char-boundary safe (invariant 4), with
tests covering Cyrillic and emoji. `TurnSpec.tool_output_limit` is threaded
from `[context] tool_output_limit` through `app/mod.rs`, `app/multichat.rs`,
and both harness call sites; sub-agents inherit the spawning turn's value via
`ToolExecContext`/`run_sub_agent`'s new parameter.

Applied in `run_agent_loop` right after `execute_tool_call`: only the
**content** argument of `ChatMessage::tool_with_display` is capped. `display`
(the UI preview), `AppEvent::ToolDone`, and `ToolCallInfo.result` keep the
full text. The `debug_log` trace keeps logging the uncapped result and gained
`result_capped`/`result_chars_sent`, so the harness trace never shows text
the model did not receive (invariant 11). `run_sub_agent`
(`src/agent/sub_agent.rs`) had its own tool-result path that bypassed the cap
entirely — it dispatches via `dispatch_generic_tool`, never touching
`execute_tool_call` — so it now takes `tool_output_limit` and caps too.

Four findings worth keeping in mind for the next rungs:

1. **A number copied from another product carries the context it lived in.**
   The plan said "tool output — 2000 chars", citing Cline, opencode and Pi.
   Re-reading them during implementation: in all three, that 2000 is the
   limit applied when **serialising history for the summariser**, not when
   writing to history. At capture, Codex uses 10 000 bytes. Capping a
   `cargo test` log to 2000 chars at capture would break ordinary work. So
   the config default is now **10 000**, and 2000 returns later as a
   separate summariser-side limit at rung 3. `.docs/context-compaction.md`
   §4's tool-output row is now split in two to distinguish the pair.
2. **The sub-agent path was a hole.** `run_sub_agent` dispatches tools
   directly via `dispatch_generic_tool`, never touching `execute_tool_call`,
   so any history-rewriting rung must be applied twice or it silently covers
   only the main loop. Recorded as a standing warning in
   `.docs/context-compaction.md` §3 for rungs 1-3.
3. **The loop's effect on what the model receives was previously
   unobservable from a test.** `FakeProvider` discarded the request. It now
   records every request (`FakeProvider::request(n)`), which is what made an
   end-to-end test of the cap possible — and every remaining rung changes
   exactly this, so the capability is a prerequisite for testing them at all.
4. **The new test was probe-verified**: reverting the cap at the application
   point makes it fail with `capped, got 5008 chars`; the probe was then
   removed. The test is known to be able to fail, not merely green.

`cargo fmt --all -- --check` clean, `cargo clippy --bin pooprusteek -- -D
warnings` clean, `cargo test --bin pooprusteek`: 521 passed, 0 failed, 4
ignored. Not run: the headless harness, live scenarios, the semantic MRR
eval.

## Context compaction — step 3 (rung 1: clear old tool bodies) + `read_file` + multi-turn harness

Findings first — this is the part worth remembering.

1. **The plan's own §2.1 was ignored by its own implementation.** Rung 1 was
   built to clear old tool-result bodies from local history, but DeepSeek's
   `build_prompt` sends only the tail after the last assistant message
   (server holds the rest), so a cleared message was never going to be
   re-sent — the disk spill bought nothing. Live evidence: every request in
   a trace was exactly 10337 chars regardless of how much history had
   accumulated, and the cleared marker never once appeared in an outgoing
   prompt. `cargo test` stayed green throughout, because `FakeProvider`
   defaults to the OpenAI-compatible shape (whole array resent every step) —
   the mismatch was invisible to unit tests and **only running it and
   reading the trace caught it.** Fixed with a new
   `LLMProvider::keeps_server_side_history()` (default `false`; `true` for
   `DeepseekProvider`, carried through `fork()`); `prune_tool_output` in
   `agent/runner.rs` returns immediately when it is true, logging
   `context.prune.skipped reason=server_side_history` once per turn, not
   once per step. `FakeProvider` gained a matching
   `.server_side_history()` builder so the split itself is unit-testable
   (`rung_one_does_nothing_when_the_provider_keeps_the_history`). Status bar
   appends ` srv` to `ctx:` for such a provider — the number is what the
   server has accumulated, not what gets sent each step.
   `.docs/context-compaction.md` §2.1/§4/§5.3 rewritten to match.
2. **"Check at turn boundaries" is nearly meaningless for this agent.** The
   original plan (and step 1/2's implementation) checked once per turn. A
   live run did 14 steps and 11 tool calls inside **one** turn — a
   boundary-only check would never have fired. `prune_tool_output` now runs
   before every step in `run_agent_loop`, with the in-flight tail —
   everything after the last assistant message, `prune::in_flight_tail_start`
   — protected unconditionally in `plan_prune`: clearing a result the model
   has not yet answered would make it reply to its own call. Both properties
   have a dedicated regression: `an_old_tool_result_is_cleared_mid_turn`
   (clears only once the result is settled) and
   `a_tool_result_the_model_has_not_answered_yet_is_never_cleared` (an
   absurdly low `preserve_recent_tokens` still can't touch it).
   `.docs/context-compaction.md` §5.3 reverses its earlier "boundary only"
   decision and explains why in the same terms Goose used to justify the
   opposite choice.
3. **The harness could only ever test one turn per scenario**, so nothing
   that happens *between* turns — clearing, session reset, summarising — was
   reachable at all. Fixed: `Scenario` gains `prompts = [...]` beside the old
   `prompt` (mutually exclusive, folded into one `turns()` accessor by
   `Scenario::from_toml`), `harness::ExecArgs.prompts: Vec<String>` (clap
   `num_args = 1..`), and `exec_args` passes every turn after a `--`
   separator so a prompt starting with `-` is never read as a flag.
   `driver::drive` loops over the prompts, driving one accumulating
   `Conversation` (`Conversation::fresh_main`) and one provider session
   through however many `TurnSpec`s that takes, under **one** wall-clock
   `timeout` for the whole run (not per turn), and stops early if a turn
   times out, errors, or loses its event channel. `RunOutcome`/`ScenarioReport`
   gained a `turns` field; the trace gained `harness.turn.started`
   (`turn`/`of`/`prompt`/`history_messages`). New
   `sandbox/scenarios/live/multi-turn-history.toml` (3 turns, `repeat = 2`)
   exercises it end to end. This was a prerequisite, not a nice-to-have —
   every between-turn behaviour in the whole compaction ladder was
   untestable before it.
4. **`exec --save-session` was writing sessions with no assistant messages at
   all.** The driver rebuilt its transcript from `AppEvent::AddMessage`
   only, which `run_agent_loop` never sends for assistant text — that comes
   as streamed `AgentChunk`s, applied to the TUI's own `Conversation` via
   `begin_assistant_message`/`append_chunk`/`discard_empty_assistant`, none
   of which the driver was listening for. Every session `exec` ever saved
   was missing its own answers. Those files feed `harness mine --sessions`
   and the semantic history index, so this silently corrupted the harness's
   own corpus since the day it shipped (2026-08-25). Fixed by having
   `drive` apply the same three events the TUI does, to the same
   `Conversation` type — turn two now sees exactly what turn two in the TUI
   would see. Regression: `a_second_turn_is_sent_the_first_turns_history`
   asserts the second request literally contains the first turn's answer
   text. **Recorded as its own RESOLVED entry in `BUGS.md`** — this is a
   defect, not a design note.
5. **CI's clippy (no `--all-targets`) treats test-only code as dead**, so it
   silently vetoes groundwork for a rung that has not shipped yet. Already
   recorded once on step 1 (`is_over`/`remaining`/`preserve_recent_tokens`
   with its `MIN/MAX_PRESERVE_TOKENS`); it happened again this batch
   (`ContextSpec::disabled()`, written and tested ahead of rung 2, deleted
   for the same reason) — two occurrences now, same root cause, same fix
   (land the helper only with the rung that calls it in the shipping build).

Also, unplanned but part of this diff: several config sub-structs
(`SemanticConfig`, `SkillsConfig`, `UpdateConfig`, plus partial-fill cases
for `ServerConfig`/`ProviderModelsConfig`) had fields with no
`#[serde(default)]` at all, so a minimal `[semantic]\nenabled = false`
harness config — exactly the kind `--config <throwaway.toml>` is meant to
support — failed to parse outright. This is the same class of bug as
review finding #2 (closed earlier this same journal file for
`Config`/`Provider`/`Ui`/`AgentConfig`), just in structs that fix missed;
now closed for these five too, with a regression test per struct.
