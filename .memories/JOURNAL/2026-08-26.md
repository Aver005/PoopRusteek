## Fixed

**#1 (Critical) — `util::atomic_write` could lose data entirely, not just
truncate it.** The `#[cfg(windows)]` block removed the target file before
`rename` on the claim that `std::fs::rename` fails when the target exists on
Windows — false; `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` already
replaces. The remove opened a window where a crash left *no* file at all,
worse than the truncation the function exists to prevent. Also folds in #12
(Medium): `File::sync_all()` before the rename (data ordered ahead of the
rename, no zero-length file on crash) and a unique temp name (pid +
process-wide `AtomicU64`) so two concurrent writers to one path can no longer
share a temp file; best-effort temp cleanup on failure. Three tests, replacing the old combined one (net +2).
`→ src/util.rs` (`atomic_write`)

Consequence: `src/app/persist.rs`'s module doc no longer cites the fixed
`.tmp` path as a reason to serialize writes — only the snapshot-ordering
reason still holds.

**#2 (Critical) — a config.toml missing one section or key failed to parse,
and the TUI silently fell back to full defaults for the whole run.** Only 8
of 12 `Config` sections/fields carried `#[serde(default)]`. Fixed:
`provider`/`ui`/`agent`/`mcp` got `#[serde(default)]` on `Config`, and every
scalar field of `ProviderConfig`/`UiConfig`/`AgentConfig` got
`#[serde(default = "named_fn")]` with a named function per field — not a bare
`#[serde(default)]`, which would have zeroed `max_steps_per_turn`/floored
`auto_compact` to `false` instead of the real defaults (256 / true). The three
structs gained `Default` impls built from those same functions; `Config`
itself now derives `Default` (its hand-written impl is gone). No
`deny_unknown_fields` added — an older config with a stale key must keep
parsing. Four new tests, including a regression for the bare-`default`
zeroing trap. `→ src/config/mod.rs`

**#5 (High) — CORS was wide open regardless of whether auth was configured.**
`Access-Control-Allow-Origin: *` and its two sibling headers went out on every
`/serve` response unconditionally, while the bearer check only engages when
`api_key` is `Some` (default `None`). With no key set, any web page the user
had open could cross-origin `POST /v1/chat/completions` to loopback and read
the reply — driving the user's DeepSeek account and any `[[providers]]` keys.
Fixed: the three headers now go out only when `context.api_key.is_some()`.
One test over a real loopback socket asserting `/health` and the `OPTIONS`
preflight agree, and that headers are absent with no key configured.
`→ src/server/http.rs`

**#11 (Medium) — bare `String::from_utf8_lossy` on child stdout/stderr in the
harness itself**, violating invariant 4 in code that postdates the invariant.
Both call sites replaced with `crate::util::decode_process_output`.
`→ src/harness/scenario.rs`

**#16 (Low) — `sandbox/config.template.toml` advertised three `[ui]` keys
that no longer exist** (`show_status_bar`, `show_line_numbers`,
`max_message_length` — `UiConfig` holds only `theme`/`custom_themes` since the
2026-07-15 sweepables pass). Dropped from the template.
`→ sandbox/config.template.toml`

## Vision Stage 0 — `/attach` no longer drops files silently

Not a review finding; Stage 0 of `.docs/vision-local-image-understanding.md`
(a separate research doc — see MAP.md), closing its §1.1: `submit_input`'s
attachment inlining used `read_to_string(...).ok()?` inside a `filter_map`, so
a PNG vanished entirely on `InvalidData` — the status bar still said "1 file
attached" but the model received nothing and had no way to know an attachment
existed.

Fixed: the inlining logic moved into a pure `build_attachment_section` helper
that always records the display name and always emits a block. Not-UTF-8
content becomes `"Image file / Binary file — content not read as text."`
(chosen by `AttachedFile.is_image`); any other open failure reports the OS
error text instead of being mistaken for binary content. Four new tests.
Stages 1–4 of the vision plan (OCR tool, ONNX captioning, remote backend, MCP
screenshot passthrough) are untouched. `→ src/app/keys/chat.rs`
(`build_attachment_section`)
