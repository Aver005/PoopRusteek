# 2026-08-25 — headless harness + Docker sandbox

Goal set by the owner: make it possible to test the product **autonomously**,
without a human driving the TUI — "test live answers through the service
itself and extract the important patterns". The proposal was a Docker Desktop
sandbox with full CLI control.

## The finding that shaped the work

Docker alone does not close the goal. The blocker was not isolation, it was
that **nothing headless runs the agent loop**:

- `--acp` — 190 lines, a bare prompt relay, no tools, system prompt hardcoded
  to `"You are Pooprusteek, a helpful AI coding assistant."`
- `--proxy` / `--serve --uiless` — a provider gateway. Stateless per request,
  and inbound `tools` are explicitly discarded with a `tracing::warn`
  (`server/openai.rs::chat_completions`).

`AgentRuntime::spawn(TurnSpec)` was reachable only from `App`, and its only
observable output was `AppEvent` — not even `Serialize`.

So the keystone was a third headless mode, and the container is the box
around it (necessary: a harness answers approvals from a policy, and the tool
set includes a shell).

## Built

**`src/harness/`** — `exec` / `scenario` / `suite` / `mine` / `mock-provider`
subcommands on the existing binary. Bare invocation still starts the TUI, so
no existing usage changed. Full reference: `reference/HARNESS.md`.

**Trace = the debug log, in JSONL.** The decision worth remembering: no new
instrumentation went into the agent loop. `runner.rs` was already dense with
`debug_log` calls carrying exactly what a trace needs
(`agent.step.parsed.payload` has the raw model output, visible text, parsed
calls and parse errors). A second telemetry stream would have drifted. So
`debug_log` gained `Format::Jsonl` + `configure(path, format)` + a monotonic
`SEQ`, and the harness adds only `harness.*` records for what it alone knows.

**`auto_approve` stays false** in headless runs. `run_agent_loop` refuses
sub-agents when it is on ("Nested sub-agents are not allowed", depth limit 1),
so the lazy path would have made sub-agents untestable. The driver answers
approvals from an `ApprovePolicy` instead — real approval path, testable
denial, working `task` tool. `scenarios/live/spawns-sub-agent.toml` now guards
that property.

**Scenarios repeat, and run as children.** One sample of a nondeterministic
model is not evidence, so a scenario declares `min_pass_rate` and the report
carries rates plus min/median/max. Each repeat is a `pooprusteek exec --json`
child process: one trace file per repeat (the debug sink is process-global),
no state bleed, and a wedged turn killable without taking the runner down.

**Mock provider.** A scripted OpenAI-compatible endpoint (same
`openai_compat` client, same streaming path, same tool parser) so behaviour
can be regressed deterministically and failure paths the live model reaches
only by accident can be driven on demand. Its JSON is hand-rolled rather than
reusing the app's serializers — a double sharing wire code with the thing
under test cannot catch a wire bug.

**`sandbox/`** — two-stage Dockerfile, compose (one-shot `sandbox` +
long-running `mock`), `sandbox.ps1` / `sandbox.sh`, fixtures, 5 live + 2 mock
scenarios, 3 mock scripts, README.

**Supporting changes to the app:** `--config <file>` (global; keeps a harness
run off the real config and token, fatal if an explicit path is unreadable),
`App::effective_mcp_schema_mode` moved to `Config` so the TUI and the harness
build identical prompts, `app::system_prompt` made public.

## Verified live

Against the throwaway DeepSeek account, on the host:

- trivial answer, no tools: 1 step, ~2.1s, 3/3 repeats pass
- tool-using turn in a fixture repo: 2–3 steps, 1–2 `powershell` calls,
  median 5.7s, 3/3 pass
- mock: the scripted malformed `<tool_use>` → parser feedback → corrected
  call → answer sequence, reproducible every time
- `mine` over 9 traces + 15 saved sessions produced ranked buckets

474 tests (was 434), `clippy --bin pooprusteek -- -D warnings` clean, fmt
clean.

## What the harness caught immediately

1. **It contaminated the environment it measured.** A relative `--trace` path
   was resolved *after* `chdir` into the workspace, so the trace directory was
   created inside the directory under test and the agent listed it as part of
   the workspace. Fixed (`absolutize` before `chdir`). Filed under RESOLVED in
   `BUGS.md`.
2. **UTF-16 tool output decoded as UTF-8** — found, then fixed. `bash` on
   Windows resolves to WSL; `wsl.exe` writes its own diagnostics in UTF-16LE
   while `shell.rs` decoded every pipe with `from_utf8_lossy`, so a WSL mount
   failure reached the model as `\x1d\x045\x04 \x00C\x04…`. The existing
   `POWERSHELL_UTF8_PREFIX` covers only the sibling OEM-codepage case.

   Fix: one shared `util::decode_process_output` replacing four scattered
   `from_utf8_lossy` calls. Detection is BOM first, then which side of each
   byte pair carries a byte that cannot occur in text (< 0x20 excluding
   tab/CR/LF, or 0x7F). My first attempt counted NULs and **failed its own
   test**: `Н` (U+041D) encodes as `1D 04`, so a Russian message contains no
   NULs at all — only Latin text produces them. Both streaming readers now
   keep raw bytes, as their doc comments already claimed; decoding per line
   cannot work when the newline is `0A 00` and `read_until` therefore returns
   half-aligned chunks.
3. Two defects in the harness's own analysis code: `message_field` cut values
   at the first space (`errors=tool \`bash\`: … not valid JSON` collapsed to
   `tool`), and the loop detector counted repeated code fences as loops.

## Docker: two distinct build problems

**1. glibc, not a Dockerfile bug.** `rust:1.91-bookworm` cannot link this
crate: the prebuilt static ONNX Runtime that `ort` downloads is built against
glibc >= 2.38, where `strtoll`/`strtoull` are redirected to the C23 symbols
`__isoc23_strtoll` / `__isoc23_strtoull`. Bookworm is glibc 2.36 and has
neither, so `libort_sys` fails to link. Both stages moved to trixie
(`rust:1.91-trixie` + `debian:trixie-slim`). Worth remembering as a general
constraint on which Linux bases can build this crate.

**2. Build flake worth knowing**

Two builds died mid-compile with the daemon dropping the connection
(`rpc error: code = Unavailable … EOF`, then `_ping` 500 and a Docker Desktop
crash). Not a Dockerfile error: unbounded parallel rustc plus the ort/wasmtime
link step exhausts the WSL2 VM. Same failure class as the host-build flake
already documented in `CLAUDE.md`. Mitigated with `CARGO_BUILD_JOBS=4` (build
arg, overridable) and a `BUILD_PROFILE=dev` option for fast validation.

## Defects the sandbox found in the harness itself, once it ran in a container

- The `mock` service outlives a turn, so its reply cursor was still at the end
  of the script when a second repeat started — repeat 2 of a scenario silently
  tested something different from repeat 1. Fixed: the cursor rewinds when a
  request carries a single non-system message, which is exactly what
  distinguishes a fresh turn from a later step of the same one.
- Git Bash rewrote `/out/x.jsonl` into `C:/Program Files/Git/out/x.jsonl`, so
  the first container run wrote its trace nowhere useful. Excluding only the
  two container prefixes via `MSYS2_ARG_CONV_EXCL` fixes it; disabling
  translation wholesale was worse — it broke the host-side `--env-file` path.
- `init: true` in compose plus tini in the entrypoint left tini not-PID-1 and
  warning it could not reap. Compose's init removed.

## Verified in the container

`sandbox.sh doctor` clean; a live turn answered in 13s with the trace landing
in `sandbox/out/`; `scenario shell-reads-workspace 2` → 2/2 passed, `bash×2`,
median 3.9s — faster than on the host, where WSL's broken bash had pushed the
agent to PowerShell. 484 tests, clippy gate clean.

## Part 2 — pointing the harness at real developer tasks

The live scenarios proved the harness worked; they did not resemble what
anyone actually asks an agent to do. Four `dev` scenarios do: build a static
todo page from an empty directory, fix a failing unit test, create exactly two
files and nothing else, explain code without touching it.

Two gaps surfaced immediately. Fixtures were mounted read-only, so a task that
writes had nowhere to go, and repeats would have seen each other's files.
`workspace_template` copies a template into a fresh scratch directory per
repeat, kept next to the trace so the output can be read afterwards. And every
expectation looked at the answer text, which for this kind of task is the least
reliable evidence there is — `files_exist` / `files_absent` / `file_matches`
judge what came out instead. `python3` went into the image so the red-to-green
loop could run at all.

### Finding 1 — an empty reply counted as success

First run of the page scenario: 2/3 passed, and the third made one step, zero
tool calls, and reported `turn.done status=success` in 1.4s with an empty
directory. The provider had closed the stream with zero bytes and the loop
ended the turn on it. Fixed: nudge and retry, bounded, then report an error
saying plainly that nothing was changed.

### Finding 2 — the empty replies were an unparsed rate limit

Why the stream was empty is the better question. The trace had the answer two
lines above, logged as `completion.stream.skipped`:

    event: hint
    data: {"type":"error","content":"消息发送过于频繁，请稍后重试",
           "clear_response":true,"finish_reason":"rate_limit_reached"}

HTTP 200, an explicit rate limit *inside* the stream, then a clean EOF that the
client read as a normal stop. The parser recognised no such frame, so an
error the provider had stated outright became an empty success. Now parsed and
reported; rate limits wait and retry with backoff, but only while no text has
reached the caller, since a retry after partial output would duplicate it.

Note the self-inflicted part: the sandbox config had throttling off, which is
what tripped the limiter. 1200ms plus backoff is the current setting, and the
account is tight enough that a four-scenario suite still draws limits.

### Finding 3 — announcing the work counts as finishing it

The one that is not a code bug. A run that *did* get through:

    step 1  bash: ls -la
    step 2  "Директория пуста, только .gitkeep. Создам три файла."  → turn done

No tool call in step 2, so the loop treated the text as the final answer. The
model announced the work and stopped; the harness scored it `completed` over an
empty workspace. A user would see a confident sentence and no files.

This is the interesting failure mode, because it is invisible to every check
that reads the answer text and obvious to one that reads the filesystem. It is
also the natural first experiment for prompt wording rather than code: can an
instruction remove the behaviour, and at what cost elsewhere. Recorded in
BUGS.md under HIGH.

### Numbers

497 tests, clippy 0, fmt clean. `dev` suite at 3 repeats, after both fixes:
explains-without-writing 3/3, respects-explicit-constraints 2/3,
fix-failing-test 1/3, greenfield-todo-page 0/3 — with rate limits still
accounting for most of the misses, which is why the throttle matters before
any of these rates are treated as evidence about the model.

## Part 3 — comparing system prompts

The announce-and-stop failure looked like a prompt problem, so the harness
learned to vary the prompt: `system_prompt_append` on a scenario, a file
appended to the assembled prompt, recorded in the trace. Four variants over
three tasks, siblings differing in exactly one field.

- **A — baseline**: the prompt as shipped.
- **B — finish the work**: an explicit rule against ending a turn on an
  announcement.
- **C — verify before claiming**: B, plus "confirm the result with a tool
  before you say it exists".
- **D — role framing**: tone only, no rule — the control for whether a stated
  rule beats general exhortation.

### What was measured

28 runs scored, 16 lost to the provider's quota (the whole `constraints`
control group and `fixtest/D-role`).

| task | variant | pass | in-chat | fail | excluded | scored | steps/calls |
|---|---|---|---|---|---|---|---|
| greenfield | A-baseline | 4 | 0 | 0 | 0 | 4/4 | 6.0 / 5.0 |
| greenfield | B-finish | 3 | 1 | 0 | 0 | 3/4 | 4.8 / 3.8 |
| greenfield | C-verify | 4 | 0 | 0 | 0 | 4/4 | 6.0 / 5.0 |
| greenfield | D-role | 4 | 0 | 0 | 0 | 4/4 | 5.5 / 5.0 |
| fixtest | A-baseline | 3 | 0 | 1 | 0 | 3/4 | 5.0 / 4.0 |
| fixtest | B-finish | 4 | 0 | 0 | 0 | 4/4 | 7.0 / 6.0 |
| fixtest | C-verify | 3 | 0 | 1 | 0 | 3/4 | 5.8 / 4.5 |
| fixtest | D-role | — | — | — | 4 | none | — |
| constraints | all four | — | — | — | 12 | none | — |

### What it says

**No variant is distinguishable from the baseline.** Every difference is one
run at n=4, which is noise. The result worth reporting is the negative one,
and two observations explain it.

First, **the failure being targeted barely occurred**. In 28 clean runs the
announce-shaped ending happened once — under B, the variant designed to
prevent it, where the model wrote "Создам три файла:" and then the file
contents as a markdown block instead of calling a tool. Earlier, when runs
were competing with the rate limiter, the same shape appeared in roughly one
run in three. That is a correlation worth chasing: the behaviour may belong to
provider stress rather than to prompt wording.

Second, **C instructs what the model already does**. Every baseline run ends
with a verification call of its own — `ls -la`, `head index.html`,
`python3 -m unittest discover`. An instruction that describes existing
behaviour cannot improve it, and the identical 6.0/5.0 step and call counts
for A and C on greenfield say it changed nothing at all.

The one signal that is not noise-shaped is **effort**: on `fixtest`, B ran
7.0 steps / 6.0 tool calls against the baseline's 5.0 / 4.0. If prompt wording
moves anything here, it looks like how much work the model does per turn
rather than whether it succeeds — but that needs a task with enough headroom
to show it, which these did not have at 4/4 baselines.

### Hypotheses worth testing

1. **Announce-and-stop is provider-stress-correlated, not prompt-correlated.**
   Testable now, and deterministically: script `mock-provider` to truncate or
   stall mid-response and see whether the shape reproduces without any rate
   limiter involved, and whether wording changes recovery.
2. **Prompt wording moves effort, not success.** Measure steps and tool calls
   as the outcome on a task the baseline does not already pass, rather than
   pass rate on one it does.
3. **These tasks are too easy to discriminate.** A 4/4 baseline leaves no room
   to improve. Needed: a failing test whose cause is not on the first
   traceback line, a change spanning several files, a task with a constraint
   that conflicts with the obvious approach.
4. **n=4 cannot answer this question.** Separating a 25-point difference needs
   tens of runs per cell. The binding constraint is the account's quota, not
   the harness — so this line of work needs the mock provider, a second
   account, or both.
5. **An instruction only helps where behaviour is missing.** C is the evidence:
   it prescribed a verification step the model already performed. Before
   writing a rule, check the traces for whether the behaviour is absent.
6. **The `constraints` control still has to run.** A prompt that pushes harder
   for action is exactly the kind that starts creating files nobody asked for,
   and that risk is unmeasured.

### Method notes

Rate-limited runs are excluded from the denominator rather than counted as
failures — they say nothing about the prompt. `sandbox/analyze-prompt-ab.py`
does this, and classifies by mechanism (announce / wrote-it-in-chat / other)
rather than by pass alone. It reads only the newest report per pair, because
the directory also holds earlier attempts that ran against a broken image.
