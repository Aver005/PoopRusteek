# 2026-10-19 — аудит саб-агентного режима и тайм-аутов, марафон по этапам

Просьба владельца: проблемы прячутся, когда бинарь работает саб-агентом;
тайм-ауты ведут себя странно; непонятно, что будет, если ответ не придёт.
Сначала большой аудит тремя агентами по разным направлениям, потом план и
закрытие всего с коммитом после каждого этапа.

Аудит: `reference/AUDIT-2026-10-19-SUBAGENT.md` (≈90 уникальных находок после
склейки трёх отчётов). OpenCode-ключ просрочен — аудиторы и ревьюеры через
обычных агентов.

## План

1. Зависания и паники — страховочная сетка (1.x).
2. Правда для модели — ошибки, коды выхода, причины провала (2.x).
3. Контракт суб-агента `task` (3.x).
4. Вердикт `exec`/`scenario` (4.x).
5. Провайдеры, повторы, MCP, `/serve`, ACP (5.x).
6. TUI: чаты, GOAL, процессы (6.x).
7. Документация, навык `pooprusteek-subagent`, CHANGELOG.

Каждый этап: правки → тесты → ревью тремя агентами → коммит.

## Журнал действий

### Этап 0 — clippy нового тулчейна (`be5d63b`)
clippy 2026-09 ругает `double_must_use` на трейтах `#[async_trait]` — ошибка
была и на чистом HEAD, хук бы не пустил ни один коммит. `allow` на трёх трейтах.

### Этап 1 — зависания и паники (`32e3153`)
Сделано: 1.1–1.12 аудита. Ревью трёх агентов нашло главное: на Windows
`taskkill /T` из гарда стартовал после того, как `kill_on_drop` уже убил
корень, — внуки выживали, а переиспользованный PID мог погибнуть чужой. Итог:
`ProcessTree` (своя Job Object без kill-on-close / своя группа + `kill(-pgid)`),
синхронно в `Drop`, `release()` сразу после `wait()`. Глобальный
`FOREGROUND_CHILD_PID` удалён — Esc больше не бьёт команду чужого чата.
Повторная проверка нашла ещё: привязку к общей kill-on-close задаче (убивала
бы `start notepad` при выходе) и `shutdown_signal()`, создаваемый заново на
каждой итерации `select!` (сигнал между итерациями терялся).
Сознательно не сделано: процесс, держащий пайп после выхода команды, не
убивается (так держит пайп и нарочный `start notepad`) — модель получает пометку.

### Этап 2 — правда для модели (`053f2db`)
Сделано: 2.1–2.13. По ревью: заметка о провале — с потолком и в кавычках;
у Anthropic/Gemini системные заметки из середины истории поднимались в system
prompt (копились навсегда) — теперь остаются на месте текстом `[Note]`;
ярлык истории `[TOOL: имя]` совпадал с открывающим тегом старого формата
вызова — стал `[TOOL RESULT: имя]`; MCP-сервер «ломается» только после 3 сбоев
подряд и только тот же клиент (`Arc::ptr_eq`).
Перенесено в этап 3: общий модуль текстов для обоих циклов, суб-агент на тех
же решениях (`turn_failure`, лимит вывода, спасение при тайм-ауте).

### Уроки этого захода
- `git stash`/`pop` на этой машине оставил файлы с CRLF — не пользоваться,
  для выделения коммита — выборочная индексация ханков.
- Нельзя делить `CARGO_TARGET_DIR` с git worktree: build.rs вшивает абсолютный
  путь к `pooprusteek.res`, и после удаления worktree основная сборка не
  линкуется (`LNK1181`) и тесты путей падают. Лечение — `cargo clean -p pooprusteek`.
- В heredoc этого Bash двойной обратный слэш становится одинарным: строки с экранированием
  писать только через Edit.

### Этапы 3+4 — контракт суб-агента и вердикт `exec` (`fa6b95c`)
Один коммит: харнесс водит суб-агентов по тому же новому контракту, порознь
не собирается. Суб-агент `task` — обычный `run_agent_loop` через
`app::runtime::run_guarded` внутри future родителя; подтверждения уходят
родителю с полем `origin`. `TurnSpec.auto_approve` удалён совсем — в
продакшене не осталось флага, который обходит подтверждение; тестовые
инструменты раннера объявляют `requires_approval() == false`.
Ревью нашли (и закрыто): модалки меняли флаг занятости фокусного чата (6.1
перенесён сюда — фоновые ходы теперь спрашивают); заметка в `exec` не
откладывалась (харнесс не слал `Started`); Esc сбрасывал заметки раньше, чем
закрывал вызовы; несбалансированный `ToolStarted` при панике суб-агента;
сигнал/срок после конца корня; `broken` после тайм-аута при живой связи.
Сознательно: `exec --json` при ошибке разбора аргументов ищет `exec` и
`--json` в argv вручную — clap не отдаёт подкоманду упавшего разбора.
Осталось (этап 6): Esc всё ещё гасит фоновые задачи всех чатов
(`cancel_focused_turn` → `shutdown_all`); `apply_fetched_session` не снимает
запросы подтверждения прерванного хода.

### Этап 5 — провайдеры, MCP, `/serve`, ACP
Сделано: 5.1–5.7, 5.9–5.17 аудита. DeepSeek: повторы по политике
`Resend::{Safe, ConnectOnly}` (completion с PoW повторяется только при ошибке
соединения, 429 — заново снаружи со свежим PoW), один `RateLimiter` на все
форки со слотом под замком, `read_timeout` 90 с, срок на PoW 60 с, HTML-ответ
WAF распознаётся, лимит внутри потока не сдвигает точку сессии.
Пульс (`pulse` + `OwnWait`) бьёт только пока провайдер ждёт сам себя (сессия,
PoW, файлы, ограничитель, паузы) и не дольше 10 мин — чтение ответа стережёт
сторож простоя; старый `with_heartbeat` у вложений удалён.
MCP: операции без замка (`reload`/`reconnect`/`toggle`/`add`/`remove`),
клиент ставится и итог сливается только при `ptr_eq` с ожидаемым,
проигравший клиент закрывается. `/serve`: 429/504/502 вместо 500, keep-alive,
сброс сессии через `SessionDiscard`. ACP: ответ на любой запрос с id
(включая `"id": null`), коды JSON-RPC, ничего в stderr.
Ревью трёх агентов: главное — пульс отключал сторожа простоя навсегда
(бесконечные повторы), гонки установки MCP-клиента, Gemini глотал
`{"error":…}` (все поля его ответа необязательны).
5.8: рассуждение копится не больше `MAX_STREAM_BYTES` (`ThinkRouter::hold`).
5.18: `complete()` без сторожа, но у всех провайдеров `read_timeout` 90 с —
заглохшее соединение падает; остаётся поток из одних keep-alive (в BUGS).
Сознательно не сделано: общий насос потока для `drive_sse_bridge` и
`agent::stream::collect` (дублирование — в BUGS как долг).

### Этап 6 — GOAL, процессы по чатам, забор событий (вместе с 5 в `e915a19`)
GOAL: `GoalState.conversation`, оценщик на форке с `SessionDiscard`, строгий
`parse_goal_verdict`, счётчик `eval_failures`. Процессы: task-local `OWNER`
(`with_owner` в `run_guarded`), `shutdown_nonpersistent_of`/`shutdown_owned_by`,
убийство в фоне. Забор: `App::abort_turn_of` выставляет `Conversation::fenced`,
события и запросы чата выбрасываются до `AppEvent::TurnFenced` (его шлёт
задача, дождавшаяся конца оборванного хода). `/compact`: сбой сброса виден.
