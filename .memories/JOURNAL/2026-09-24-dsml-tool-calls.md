# 2026-09-24 — модель DeepSeek пишет вызовы в DSML, и они терялись

> Поправка 2026-09-28: «искажённая» разметка ниже — штатный формат DeepSeek
> V4.1 (` calls`/` invoke`/` parameter` с ведущим пробелом, sglang
> `deepseekv41_detector.py`); от эталона отличается только удвоенной чертой.
> См. `2026-09-28-tool-call-formats.md`.

Всплыло при проверке фикса 40005 (`2026-09-24-client-version-40005.md`):
набор `live` дал 4/6. Упали `shell-reads-workspace` (0/2 — «final answer does
not match /0\.4\.2/») и `multi-turn-history` (1/2 — «summary.md was not
created»). Ошибок провайдера и malformed нет — поток цел, ходы «успешные».

## Что оказалось

Ответ модели на первом шаге (дословно из трассы, склейка SSE-чанков):

```
I'll look at the directory contents and then read `Cargo.toml`.

<tool_use>
<name>powershell</name>
<arguments>
{"command":"Get-ChildItem -Force | Select-Object Mode, Length, Name"}
</arguments>
</tool_use><｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="read_file">
<｜｜DSML｜｜ parameter name="path" string="true">Cargo.toml</｜｜DSML｜｜ parameter>
</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
```

Второй вызов — родная разметка DeepSeek (DSML, введена в V3.2). Парсер знал
только `<tool_use>` и `[TOOL:…]`, поэтому `read_file` пропадал: агент видел
список файлов и отвечал, не прочитав `Cargo.toml`.

Маркеры **искажены** по сравнению с каноном `<｜DSML｜function_calls>`:
удвоенная черта, пробел, нет `function_`. Видимо, веб по-своему рендерит
спецтокены. Отсюда терпимый фрагмент регулярки `[｜|]+\s*DSML\s*[｜|]+\s*` и
обёртка `(?:\w+_)?calls`.

## Гипотезы и проверка

1. **Это вызвала смена `android` → `web` (веб получает другую модель).**
   Отброшено экспериментом: временно собрали с `android 1.8.0`, прогнали
   `shell-reads-workspace` ×3 — DSML в 2 из 3 прогонов, 1/3 прошёл.
2. **Это новое поведение модели.** Подтверждено: DSML есть только в трассах
   от 2026-09-24 (`grep -rl DSML .dev/harness`), в августовских прогонах его
   нет ни разу. Совпадает по дню с выкаткой «объединённых режимов» на сайте.

## Решение

- `parse_dsml_calls` в `agent/tool_parser.rs`: `invoke name=…` +
  `parameter name=… string="true|false"`. `string="true"` — текст как есть
  (код с отступами не трогаем), иначе JSON, а негодный JSON остаётся строкой
  (так же делает парсер vLLM `deepseek_v32`).
- Вызовы всех форматов сортируются **по позиции в тексте**: раньше `<tool_use>`
  всегда шли раньше `[TOOL:…]` независимо от порядка, теперь порядок — как
  написала модель.
- Незакрытый `invoke` — диагностика для повтора, не молчаливая потеря (тот же
  принцип, что у битого `<tool_use>`).
- `strip_tool_calls` вырезает DSML-блоки и одиночные `invoke` из показанного
  ответа. Стриминговый трекер не менялся: он и так обрезает видимый текст на
  первом `<`, а его побайтовая эквивалентность держится на отдельном тесте.

## Проверка

- Юнит-тесты на дословный ответ из трассы, канонический DSML с типами,
  сохранность строкового параметра, незакрытый `invoke`, вырезание из показа,
  прозу со словом DSML; после ревью — порядок форматов, терпимые формы, дубль,
  фантом, процитированный тег. 911 → 923.
- Живьём: `shell-reads-workspace` 0/2 → **3/3**, `multi-turn-history` 1/2 →
  **3/3**; DSML был во **всех шести** прогонах — то есть прошли благодаря
  разбору, а не потому что модель в этот раз его не написала.

## Ревью трёх агентов и что поменялось после

Блокирующих не было; средние закрыты в том же заходе:
- **Диагностика «оборванный invoke» срабатывала на прозе.** Ответ, где просто
  процитирован открывающий тег, получал ошибку без вызовов, и `finish_or_retry`
  отвергал хороший ответ. Теперь обрыв — только открытый `invoke name="…">`, за
  которым уже идут параметры.
- **Дубль.** Модель порой пишет тот же вызов и в `<tool_use>`, и в DSML — запись
  или shell выполнились бы дважды. DSML-вызов, совпадающий по имени и
  аргументам с вызовом другого формата из того же ответа, отбрасывается.
- **Фантомный вызов.** `<tool_use>` внутри строкового параметра DSML (например,
  содержимое для `write`) выполнялся отдельно. Совпадения внутри DSML-`invoke`
  теперь пропускаются.
- **Промпт.** DSML-вызов выполнялся без намёка, что формат не тот, — это
  поощряло дрейф. В `FORMAT_REMINDER` добавлено «другую разметку вызовов
  (DSML, invoke, function_calls) не используй».
  Эффект измерен по тексту ответов (не по всей трассе: слово «DSML» теперь
  есть в самом напоминании): DSML в 8 из 12 прогонов до правки и в 5 из 10
  после. Дрейф меньше, но не исчез — поэтому разбор нужен, промпт его не
  заменяет. Набор `live` после всех правок — **6/6** (до них 4/6).
- **Mock-сценарий** `scenarios/mock/runs-dsml-calls.toml` + скрипт
  `mock-scripts/dsml-after-tool-use.toml`: ответ `<tool_use>` + искажённый DSML;
  финальный ответ с версией достижим, только если DSML-чтение `Cargo.toml`
  выполнилось. Проверено в обе стороны: с разбором 2/2, с отключённым
  `parse_dsml_calls` — 0/1 («final answer does not match»).
- Отложенное — в `BUGS.md`, раздел «OPEN — вызовы и ответ DeepSeek после
  обновления модели». Главное из него: текст фрагментов `THINK` склеивается в
  `raw`, так что вызов из рассуждений может выполниться (не проверено живьём).

## Грабли по ходу

- **Длинный Python-патч в heredoc Git Bash трижды падал** с «unexpected EOF
  while looking for matching `''», хотя heredoc был в кавычках. Причина не
  найдена (короткий heredoc с той же `｜` проходит). Обход надёжный: скрипт
  пишется файлом (Write) и запускается `python файл.py`.
- **`cargo fmt` переформатирует только что вставленный код**, и следующий патч
  по старому шаблону не находит совпадения. Патчить до `fmt` или по короткому
  уникальному якорю.
