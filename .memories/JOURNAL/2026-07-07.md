# 2026-07-07 — Landing / input / status-bar layout fixes

Four reported visual defects on the landing screen (from a wide-terminal
screenshot), all layout-math bugs in the TUI render layer. No behavior change
beyond geometry + one status-bar label.

## FIXES

- **Input first line hugged / cursor spilled past the right edge.**
  `build_visual_lines` wrapped at `width − indent` with no right margin, so a
  full first line filled to the last column and the cursor clamp
  (`area.width − indent`) put the caret one cell *outside* the box. Added a
  `RIGHT_MARGIN` (1) reserved in both the wrap width and the cursor clamp.
  (`src/tui/widgets/input.rs`)
- **Wrapped / continuation lines were indented one column past the first.**
  The `" >  "` prompt is 4 wide but continuation lines used a **5**-space
  indent (and `build_visual_lines` / `cursor_pos_inner` matched that 4-vs-5
  split). Unified everything on a single `GUTTER = 4`; removed the now-dead
  `cursor_visual_in_logical`. First and subsequent lines now start in the same
  column.
- **Recent-sessions date clipped to "Jul".** The row concatenated
  id(≤17)+title(≤31)+model(unbounded)+date(12) ≈ 84 cols into a 76-col table,
  so the Paragraph truncated the trailing date. Rewrote `render_sessions_table`
  to budget columns to the (centered) width: fixed id/model/date slots, `title`
  flexes to fill the remainder, `RIGHT_PAD` keeps it off the last column. New
  `util::fit_col(s, width)` truncates-with-… **and** pads to an exact display
  width (multibyte-safe via `UnicodeWidthStr`) — Cyrillic titles stay aligned.
- **Bottom-right "2026-07-" looked like a cut-off date.** It was
  `session_prefix` = first 8 bytes of a `create_session_id` timestamp id
  (`2026-07-04T23-32-11-123Z-<uuid8>`) — not width-clipped, just a misleading
  slice. New `view_model::session_label` parses the leading `%Y-%m-%dT%H-%M-%S`
  and renders `"MMM DD HH:MM"` (e.g. `Jul 04 23:32`); non-timestamp ids fall
  back to `session_prefix`. Status bar now uses it.

## NOTES

- `GUTTER` / `RIGHT_MARGIN` are consts in `input.rs`; the `" >  "` and `"    "`
  prefix literals must stay 4 wide to match `GUTTER`.
- Tests added: `util::fit_col_*` (pad/truncate, multibyte), `view_model::
  session_label_renders_timestamp_ids_as_dates`. Full suite 398 pass, fmt +
  clippy clean.
- The landing input box is `min(width, 76)`; the chat-view input is full width.
  Both call the same `render_input`, so all four input/gutter/margin changes
  apply to both.

# 2026-07-07 (pt.2) — Frozen agent on malformed tool_use + orphaned powershell

Two independent bugs from one user report ("агент перестал что-либо делать",
then 6 `powershell.exe` stuck under the parent shell after a force-close).
Diagnosed from a saved session (`.dev/…59f8cfe3.json`), the two
`tool_parser: Failed to parse <tool_use> body: expected value at line 1
column 1` log lines, and the real model output pulled from the DeepSeek share
via Playwright.

## ROOT CAUSE

DeepSeek emitted a `<tool_use>` block to run `Start-Process
"C:\Users\Aver\strawberry_highlighted.png"` **twice malformed**:
1. swapped closing tags — `…</tool_use>` *before* `</arguments>`. `XML_TOOL_RE`
   (non-greedy) cut the body at the first `</tool_use>`, so `<arguments>` had no
   closer, `XML_ARGS_RE` missed, the code fell to the bare-JSON branch, and
   `serde_json` on a body starting with `<name>` gave *exactly* "expected value
   at line 1 column 1".
2. invalid JSON — unescaped quotes around the Windows path
   (`"Start-Process "C:\…""`).

`parse_tool_calls` **silently dropped** both (a `tracing::warn` to the log file
nobody watches), `strip_tool_calls` erased the block, and the runner saw
`tool_calls.is_empty() && visible_text.is_empty()` → `AgentDone` with nothing
shown, nothing run. Every following user turn repeated it → "frozen".

The same unbalanced quote is *also* why powershell hung: passed to
`powershell -Command`, an unterminated string blocks waiting for input; the job
is spawned `DETACHED_PROCESS` + `stdin=null`, so it hung detached. Detached jobs
are only reaped by `shutdown_all` (graceful exit) / `shutdown_nonpersistent`
(pre-turn) — a force-close skipped both, orphaning them under the grandparent
shell.

## FIXES

- **Parser tolerance + diagnostics** (`src/agent/tool_parser.rs`). New
  `parse_tool_calls_with_errors() -> (Vec<ParsedToolCall>, Vec<String>)`;
  `parse_tool_calls` is now a thin wrapper (`.0`). New `extract_arguments`
  tolerates swapped `</arguments>`/`</tool_use>`, a dropped `<arguments>`
  wrapper (first `{…}` after `<name>`), and the bare `{"name","arguments"}`
  shape (was only `{"tool","args"}`). **Genuinely broken JSON is NOT repaired**
  (would risk running the wrong command) — it becomes a diagnostic. 5 tests
  added (swapped tags, bad-JSON→error, missing wrapper, name/arguments shape,
  well-formed→no errors).
- **Feed malformed calls back to the model** (`src/agent/runner.rs`). When
  `tool_calls` is empty but `parse_errors` is non-empty, push the raw assistant
  text + a `malformed_tool_feedback()` correction (naming each error + the exact
  required shape + JSON-escaping rule) and `continue` the loop instead of ending
  the turn. Bounded by `MAX_MALFORMED_TOOL_RETRIES = 2`; on exhaustion a system
  message tells the user instead of a blank turn. Works for both provider styles
  (DeepSeek re-sends only the last message = the correction; OpenAI/Anthropic
  replay full history and see the mistake + fix).
- **Windows Job Object, kill-on-close** (`src/tools/background/types.rs`
  `win_job` + calls in `spawn.rs`, features in `Cargo.toml`). A process-wide
  anonymous job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; every pipe child
  (via `child.raw_handle()`) and PTY child (via `OpenProcess(pid)`) is assigned
  to it. When pooprusteek dies — graceful, `taskkill`, or crash — the last job
  handle closes and Windows terminates the whole job tree. Assignment failure is
  non-fatal (falls back to the existing `shutdown_all` reaping). Needs
  windows-sys features `Win32_Foundation`, `Win32_Security` (gates
  `CreateJobObjectW`), `Win32_System_JobObjects`, `Win32_System_Threading`.

## NOTES

- Full suite **406 pass**, fmt + clippy clean, ort links.
- The unbalanced-quote → PowerShell-hang is a model/prompt misuse (opening a
  file should be foreground, not `background=true`); left as-is since the Job
  Object now guarantees cleanup regardless. Could later add a heuristic to keep
  fire-and-forget `Start-Process`/`Invoke-Item` in the foreground.

## Deferred MCP prompt slimmed further: server summary instead of tool list

Owner call: with RAG hints + `tool_search` both live, even the deferred
one-liner-per-tool list is context waste. `system_prompt::build`'s
deferred branch now emits ONLY a server-level summary — total tool
count, "not listed here / suggested automatically / call tool_search /
never guess names" instructions, then `- <server> (N tools)` rows
(grouped by stripping `mcp__` and splitting on `__`). Individual tool
names no longer appear in the system prompt at all in deferred mode.
The model's paths to a schema stay the same two: per-turn semantic hint
(full defs inlined for matches) and explicit `tool_search`.
`DEFERRED_DESC_MAX_BYTES` died with the per-tool lines. README/CLAUDE.md
wording updated to match. Skills side needed nothing: the prompt never
enumerated the catalog (only enabled skills' content + the `skill` tool
howto in tools.prompt.md).

# 2026-07-07 (pt.3) — Self-update system (`/update`, `/autoupdate`, `latest` release channel)

Owner request: auto-update via `/update` and/or at startup (`/autoupdate
on|off`), detected by comparing the local binary's hash against the binary
published under a `latest` tag — which didn't exist and had to be
created/re-pointed by CI whenever the develop release publishes successfully.

## HOW IT WORKS

- **CI channel** (`.github/workflows/ci.yml`, `publish` job). New step after
  artifact flattening extracts the *raw* binaries out of the three archives,
  renames them per target (`pooprusteek-windows-x86_64.exe`,
  `pooprusteek-linux-x86_64`, `pooprusteek-macos-arm64`) and writes
  `SHA256SUMS` over the **uncompressed** binaries (so hashes compare directly
  with the installed file). After the versioned `v<ver>-dev` release is
  created, three new steps force-move the `latest` tag, delete the previous
  `latest` release and publish a fresh one with the same assets/body — ordered
  last so a failed dev publish never moves `latest`.
- **`src/update.rs`** (new top-level module). `run()`: fetch
  `releases/download/latest/SHA256SUMS` → find the entry for
  `platform_asset()` → SHA-256 the current exe (`spawn_blocking`) → on
  mismatch download the raw binary, re-verify its hash, `install()`.
  `install()` renames the running exe to `<exe>.old` (legal on Windows and
  Unix while running), `util::atomic_write`s the new bytes to the original
  path (rolls the rename back on write failure), chmod 755 on Unix, then
  best-effort deletes `.old` (succeeds on Unix; Windows leaves it for
  `cleanup_stale_backup()` at next startup). 404 → "no latest release yet".
- **Commands** (`commands/defs/update.rs`): `/update` →
  `CommandResult::Update(UpdateAction::Run)`; `/autoupdate [on|off]` →
  `AutoStatus`/`SetAuto` persisting new `[update] auto` config (default
  **off** — replacing the binary must be opt-in). Interpreted in
  `apply_update_action` (keys/dispatch.rs), same pattern as `/rag`.
- **App wiring**: `app::spawn_update_task(event_tx, in_flight, quiet)` runs
  the pass off-loop and reports via new `AppEvent::UpdateStatus { message,
  notable }` (notable=false → status line only; true → also a ui_system chat
  message). `App.update_in_flight: Arc<AtomicBool>` guards concurrent passes
  (startup check + `/update` racing on the binary swap). `App::new` calls
  `update::cleanup_stale_backup()` every launch and spawns the quiet check
  when `config.update.auto`.

## NOTES / GOTCHAS

- Hash comparison means a **locally built** binary always differs from the
  released one — `/update` (or auto mode) will happily replace a dev build
  with the released build. Deliberate: the mechanism is "match the latest
  release", not "am I newer".
- `backup_path` *appends* `.old` (`pooprusteek.exe.old`) — `with_extension`
  would have replaced `.exe`. Unit-tested.
- Asset names live in exactly two places that must stay in step:
  `update::platform_asset()` and the CI extraction step (comment cross-links
  both).
- The `latest` release doesn't exist until the next successful develop push
  runs the new publish steps; until then `/update` reports the 404 cleanly.
- Tests 406 → **415** (SHA256SUMS parsing, sha256 vector, backup-path,
  install-swap round-trip on a temp file, platform-asset contract, config
  compat/round-trip, `/autoupdate` parse). fmt + clippy clean.

## REFINEMENTS (same session, post-review Q&A)

Three follow-ups after walking the owner through the mechanics:

- **No "window without binary" on install.** `install()` now **stages the
  new bytes in full** at `<exe>.new` (`atomic_write`) *before* touching the
  live binary, then a platform `promote()` swaps: Unix does one atomic
  `rename(.new → exe)` (running process keeps the old inode; zero absent-file
  window, no `.old` needed); Windows moves the live exe to `.old` then `.new`
  into place (gap is two metadata ops, not a multi-MB download; rolls back on
  the second rename failing). `cleanup_stale_backup()` now also reaps a
  stranded `.new`. Old code renamed-then-wrote, exposing the whole download.
- **Dev-build confirm.** `/update` from a `cfg!(debug_assertions)` binary
  (i.e. `cargo run`) now opens a confirm modal first (new
  `ConfirmAction::Update` + `ConfirmState::update_dev`, resolved in
  keys/modal.rs → `start_manual_update`) — a dev binary always mismatches the
  released hash, so an unconfirmed swap would replace the dev build silently.
  Release builds still update straight through.
- **Timestamp-in-hash: declined, explained.** Owner asked whether a timestamp
  could be written into the hash to get newer/older ordering. It can't — SHA
  is a one-way function of the bytes; ordering needs a *separate* key (build
  timestamp / CI run number baked into the binary + published in the
  manifest). Left unimplemented pending an owner decision on the ordering key
  and whether to hard-block downgrades. Noted in AUTO-UPDATE.md failure modes.

- **New reference doc**: `reference/AUTO-UPDATE.md` — swap mechanics, the full
  **contract-points table** (what must not desync between `src/update.rs` and
  CI), and failure modes. Linked from INDEX.md; README got an "⬆️ Self-update"
  section pointing at it. Tests unchanged at 415 (test bodies edited in place,
  no new fns), fmt + clippy clean.
