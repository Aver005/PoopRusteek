## OpenAI-compat protocol layer (`provider/openai_compat.rs`)

Owner request: a conversion module between the internal provider types and
the OpenAI Chat Completions wire format, as the foundation for (a) a future
**server mode** — pooprusteek as a local OpenAI-compatible endpoint that
existing tools can call while it internally drives the DeepSeek web API —
and (b) future OpenAI-compatible *client* providers (finally implementable
`ProviderKind::Openai`). Full plan: PLANS.md ACTIVE P1.
(Terminology note: owner wrote "OpenAPI compatable"; confirmed intent is
the OpenAI API format that existing tools speak, not an OpenAPI spec.)

Shipped as a pure data-mapping module (no I/O, no App deps) in the
provider layer:
- Wire types: `ChatCompletionRequest/Message/Response/Chunk`, `Delta`,
  `ModelList`, OpenAI `{"error": {...}}` envelope. Tolerant parsing:
  unknown fields ignored, `content` accepts string OR content-parts array
  (flattened to text), role aliases `developer`→system / `function`→tool,
  `max_completion_tokens` wins over legacy `max_tokens`; inbound `tools`
  captured (not silently dropped) so the server can warn — structured
  tool-calling translation is explicitly out of scope v1 (pooprusteek's
  tool calls are prompt-encoded text via `agent/tool_parser`).
- Inbound: `to_internal_request(req, &RequestDefaults)` (defaults supplied
  by the embedder, later from `Config`).
- Outbound: `response_to_openai` + streaming `delta_chunk` (first chunk
  carries `role: "assistant"`) / `final_chunk` (empty delta +
  finish_reason; transport adds `data: [DONE]`), all stamped from one
  `CompletionMeta` {id `chatcmpl-<uuid>`, created, model} per turn.
- Reverse direction for a future client provider: `request_to_openai`
  (filters `ui_only`, same rationale as `provider/prompt.rs`),
  `response_from_openai`, `chunk_from_openai`.
- `estimated_usage` — DeepSeek web API never reports usage (KNOWN GAPS),
  so the server will report the same `estimate_tokens` heuristic the TUI
  uses; real usage passes through when a provider has it.
- Module-level documented `allow(dead_code)` (not `expect` — the items ARE
  used under `cargo test`, which would make an expectation unfulfilled).

## Semantic skill matching (`src/semantic/`) — local RAG-lite, stage 1

Skills existed but the model had no way to *discover* them: the `skill`
tool's definition was in the prompt, but nothing listed which skills
exist, so `list`→`load` almost never happened organically. Now every
outgoing turn is matched against the skill catalog locally and the top
hits ride along as an advisory note.

**Stack (fully offline after first run):**
- Dense: `fastembed` 5.x pinned to `MultilingualE5Small` (384-dim
  quantized ONNX, ~120 MB, downloaded once into
  `Config::data_dir()/models`). e5 prefix contract enforced in
  `semantic/embedder.rs` (`query: ` / `passage: `, mixing them costs
  double-digit recall — lesson carried over from poopseek's embedder).
  Outputs L2-normalized so dot = cosine. Cargo features slimmed:
  no image models, rustls not native-tls.
- Sparse: `semantic/sparse.rs` — TF-IDF over Snowball stems
  (`rust-stemmers`; Cyrillic token → Russian stemmer, else English),
  BM25-style positive-shifted IDF, L2-normalized sparse cosine. Port of
  nc-backend's proven `createSparseVector`, minus murmur hashing (string
  keys are fine without Qdrant).
- Fusion: RRF (k=60) in `semantic/matcher.rs`; zero-score docs earn no
  rank credit. Gate: candidate must clear `min_dense_score` (default
  0.80) OR have lexical overlap; already-`enabled` skills are skipped
  (their full text is in the system prompt anyway); top_k default 3.

**Wiring (invariants respected):**
- `SemanticService::start` (in `App::new`) spawns background init —
  model download/load + corpus embed on `spawn_blocking`; the event loop
  never blocks. First run emits `AppEvent::SemanticStatus` ("Downloading
  embedding model (~120 MB, one-time)...") → status line; fastembed's
  stdout progress bar is disabled (would corrupt the ratatui frame).
- `AgentRuntime` owns the `Arc<SemanticService>` and passes it to
  `run_agent_loop`, so ALL turn kinds (focused, sidechat, sub-agent,
  goal) get hints through the single spawn point.
- The hint is appended to the runner's **local** message copy as a
  system message — per-turn ephemeral, never persisted to the
  conversation, exactly the Claude Code system-reminder pattern. Framed
  as ignorable ("may be irrelevant... otherwise ignore").
- Until init completes, `match_skills` returns empty instantly — no
  turn ever waits for the model.
- Config: `[semantic] enabled=true / top_k=3 / min_dense_score=0.80`.

**Eval harness** (`semantic/eval.rs`, nc-backend's search-quality eval
in miniature): 12-skill fixture corpus, 16 ru/en queries with expected
slug, MRR printed per-query. `#[ignore]`d (needs the model) — run
`cargo test semantic::eval -- --ignored --nocapture` to calibrate
threshold/RRF changes. Sparse-only sanity tests run in CI.

**Known limits (deliberate, stage 1):** matcher corpus is built once at
startup — toggling a skill's enabled flag later doesn't rebuild it
(worst case: hint suggests an already-loaded skill; model ignores).
Corpus text is name+slug+description only; frontmatter triggers / first
body paragraph are a quality lever for later. Next stages per the
agreed roadmap: MCP tool matching (same index, defer full schemas out
of the system prompt), then message-history indexing (persistent,
atomic_write) for /search + history_search + RAG-подпитка контекста.

**Distribution note:** `ort` with `download-binaries` fetches the ONNX
Runtime at *build* time; on Windows the runtime DLL lands next to the
binary in `target/`. Release packaging must ship it (or switch to
static linking) — flagged for Phase 5.

## Semantic stage 2: MCP tool matching + deferred schemas + `tool_search`

The stage-1 skill matcher generalized into a two-corpus system and aimed
at the bigger token sink: MCP tool schemas in the system prompt (one
Playwright server ≈ 25 tools with full parameter lists, every request).

**Refactor (no behavior change for skills):**
- New `semantic/index.rs` — `HybridIndex`: the generic dense+sparse+RRF
  ranker, extracted from the skill matcher. Returns all gated `Hit`s
  ranked; corpus types apply their own filters and top-k.
- `semantic/matcher.rs` — now two thin typed corpora over `HybridIndex`:
  `SkillCorpus` (skips `enabled` skills) and `McpCorpus` (carries each
  tool's `input_schema` in the match so hints/`tool_search` can render
  full definitions without touching the MCP manager or its lock).
- `SemanticService` reworked: shared `Embedder` + both corpora behind one
  `Mutex<Inner>`; the vestigial `Phase` enum dropped — readiness IS
  `embedder.is_some()`. `match_prompt` embeds the query once and hits
  both corpora. `raw_mcp` (unembedded tool list) is kept even when
  disabled/failed — it backs the lexical fallback.

**MCP corpus lifecycle:** `update_mcp_tools` stores the raw list
instantly and re-embeds on a blocking thread; tools arriving mid-init
are picked up when init lands (same blocking task). Wired at two points:
initial `App::new` (after `MCPManager::initialize`) and the
`McpOperationDone` handler (add/reload/toggle/reconnect all funnel
there) — fetch under a short-lived lock in a spawned task, never on the
event loop.

**Deferred schemas** (`[semantic] mcp_schemas = "auto"|"full"|"deferred"`,
default auto = defer above 12 tools): `system_prompt::build` gains a
`McpSchemaMode` param; in deferred mode the MCP section is one line per
tool (name + first description line, 160-byte cap) plus an instruction
to call `tool_search` for full definitions. Two escape hatches keep it
safe: (1) per-turn semantic hints inline the FULL definition of matched
tools in deferred mode (system prompt no longer carries it); (2) the new
`tool_search` builtin returns full definitions on demand, degrading to
lexical substring matching when embeddings aren't ready — deferred mode
can never brick tool access. When `[semantic] enabled=false`, the app
forces Full mode (`App::effective_mcp_schema_mode`) — without a real
semantic search, deferring would strand the model.

**`tool_search`** (`tools/tool_search.rs` + `register_tool_search` in the
registry): query by capability, any language; limit 1–20 (default 5);
results rendered with `util::format_tool_definition` — which moved from
`app/mod.rs` to `util.rs` because semantic/tools layers need it too
(callers in system_prompt/pickers updated).

**Eval:** `semantic/eval.rs` reworked to drive `Embedder` + corpora
directly; second `#[ignore]` MRR harness for MCP tools (15-tool fixture:
playwright/outline/context7/chrome; 12 ru/en queries). Non-model tests
cover the lexical fallback and `McpSchemaMode` resolution.

Build note: one `cargo test` run died with STATUS_STACK_BUFFER_OVERRUN /
os error 1455 ("paging file too small") — parallel rustc + ort linking
exhausted the pagefile; NOT a code error, passed clean on retry.

## Semantic stage 3: message-history index, /search, history_search

The third corpus — persistent, unlike skills/MCP. Session files stay the
source of truth; the index (`data_dir/semantic/history.json`) is a
rebuildable cache of chunked user/assistant messages + embeddings
(vectors base64 f32-LE), written through `util::atomic_write`.

**`semantic/history.rs` — `HistoryStore`:**
- `open()`: loads the file; wrong version/model/dim stamp → silent wipe
  (backfill re-embeds from session files). `chunk_text` splits on char
  boundaries (1200 chars / 150 overlap, e5's 512-token budget), never
  byte-slices (invariant #4).
- `index_session()`: per-session *message-count watermark* decides
  what's new; a shrunken message list (cleared/edited session) purges
  that session's records and reindexes from zero. Filters to
  User/Assistant, non-`ui_only`, non-empty; record timestamp =
  `ChatMessage.created_at`. 50k-record cap drops oldest, loudly.
- `search()`: hybrid dense+sparse via the shared `rrf_fuse`
  (`pub(super)` now), no dense floor — explicit lookup returns the
  closest thing.

**Feeding paths (two, converging):**
1. Live: `auto_save_session` (app/sessions.rs) → after a successful
   save, `SemanticService::index_session` (spawn_blocking; no-op while
   off/initializing — the file catches it up later).
2. Backfill: at the tail of init (after skills+MCP so they're usable
   first), `backfill_history` walks `session::list_sessions()`, skips
   sessions whose on-disk message count equals the watermark (no file
   body load), embeds the rest. First run = full history indexed.
   Background sidechats/sub-agents are never persisted as sessions, so
   they correctly never reach the index.

**Consumers:** `/search <query>` (defs/search.rs →
`CommandResult::SearchHistory` → dispatch spawns the lookup off-loop,
results flush back via `AppEvent::AddMessage` as ui_system with
title/date/role/snippet/session-id + "/load <id>" hint) and the
`history_search` tool (tools/history_search.rs, registered together
with tool_search via renamed `register_semantic_tools`; 700-byte
per-result budget). `/rag` status now shows history chunks/sessions;
`/rag reload` drops the in-memory store — init re-opens the file and
re-backfills (model change → full re-embed, satisfying "переиндексирует
всё и вся").

**E2E eval (`#[ignore]`, real model):** index 4-message ru/en session →
