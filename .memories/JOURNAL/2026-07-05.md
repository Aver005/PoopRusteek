## OpenAI-compat protocol layer (`provider/openai_compat.rs`)

Owner request: a conversion module between the internal provider types and
the OpenAI Chat Completions wire format, as the foundation for (a) a future
**server mode** — pooprusteek as a local OpenAI-compatible endpoint that
existing tools can call while it internally drives the DeepSeek web API —
and (b) future OpenAI-compatible *client* providers (finally implementable
`ProviderKind::Openai`). Full plan: PLANS.md ACTIVE P1.
(Terminology note: owner wrote "OpenAPI compatable"; confirmed intent is
the OpenAI API format that existing tools speak, not an OpenAPI spec.)

Shipped as a pure data-mapping module (no I/O, no App deps) in the
provider layer:
- Wire types: `ChatCompletionRequest/Message/Response/Chunk`, `Delta`,
  `ModelList`, OpenAI `{"error": {...}}` envelope. Tolerant parsing:
  unknown fields ignored, `content` accepts string OR content-parts array
  (flattened to text), role aliases `developer`→system / `function`→tool,
  `max_completion_tokens` wins over legacy `max_tokens`; inbound `tools`
  captured (not silently dropped) so the server can warn — structured
  tool-calling translation is explicitly out of scope v1 (pooprusteek's
  tool calls are prompt-encoded text via `agent/tool_parser`).
- Inbound: `to_internal_request(req, &RequestDefaults)` (defaults supplied
  by the embedder, later from `Config`).
- Outbound: `response_to_openai` + streaming `delta_chunk` (first chunk
  carries `role: "assistant"`) / `final_chunk` (empty delta +
  finish_reason; transport adds `data: [DONE]`), all stamped from one
  `CompletionMeta` {id `chatcmpl-<uuid>`, created, model} per turn.
- Reverse direction for a future client provider: `request_to_openai`
  (filters `ui_only`, same rationale as `provider/prompt.rs`),
  `response_from_openai`, `chunk_from_openai`.
- `estimated_usage` — DeepSeek web API never reports usage (KNOWN GAPS),
  so the server will report the same `estimate_tokens` heuristic the TUI
  uses; real usage passes through when a provider has it.
- Module-level documented `allow(dead_code)` (not `expect` — the items ARE
  used under `cargo test`, which would make an expectation unfulfilled).

Numbers: tests 267 → **277** (10 new: parsing tolerance, role aliases,
response/stream protocol shapes, ui_only-filtered round-trip, error/model
list shapes), clippy **0**.

## Multi-provider support: `OpenAiCompatProvider` + `/providers` panel

The client half of the OpenAI-compat plan, with MCP-style management UX
(owner spec: `/providers` panel, `/providers add <...>` quick form,
`/providers add` wizard).

**Provider layer**
- `config`: `Config.providers: Vec<ProviderEntry{name, base_url, api_key?,
  model}>` + `active_provider: Option<String>` (both `serde(default)` — old
  configs load untouched; backward-compat test added). `"deepseek"` is the
  reserved built-in name; `active_provider_entry()` treats stale names as
  built-in. `active_model()` picks the entry's model for display.
- `provider/openai_client.rs` — `OpenAiCompatProvider`: POST
  `{base}/chat/completions` via the `openai_compat` conversions, SSE stream
  through the existing `SseLineBuffer` (`data:` lines, `[DONE]`
  terminator, malformed chunks logged+skipped, missing `[DONE]` surfaces
  through the runner's no-stop error path), optional bearer auth, OpenAI
  error envelope surfaced on non-2xx. Stateless: `fork()` = config copy,
  no sessions. Entry's model overrides the request's (the internal model
  field is a DeepSeek-ism).
- `provider::build_provider(&Config)` — THE single construction point
  (replaced 3 inline `DeepseekProvider::new` sites: `App::new`,
  ResetProvider via new `App::rebuild_provider`, onboarding). Active entry
  → OpenAI client; else deepseek (None without token). Onboarding is
  skipped automatically when a custom provider is active (view=Chat iff
  provider built).
- `CompletionRequest.stream` and `CompletionResponse.finish_reason/usage`
  are now genuinely read (expect(dead_code) removed); `response_to_openai`
  prefers real usage over the estimate.

**UI (mirrors the MCP patterns)**
- `View::Providers` + `app/providers.rs` (state + pure validation/parse,
  tested) + `render/providers.rs` (panel + wizard modal on the popup kit)
  + `keys/providers.rs`. Panel: j/k, Enter/Space = activate (config save +
  `rebuild_provider` + fresh session id; honest status when the selected
  provider can't initialize), d = remove (built-in protected; removing the
  active one falls back to deepseek), a = wizard, Esc/q back.
- Wizard: Name → Base URL (validated, scheme http/https, trailing slash
  trimmed) → API key (masked on screen, blank = none) → Model → Confirm;
  success lands on the panel with the new entry selected ("Enter to
  activate"). Quick form: `/providers add <name> <base_url> [model]
  [api_key]` (model defaults to "default" — fine for LM Studio, Ollama
  wants a real id); parse failure falls back to the wizard, like
  `/mcp add`.
- Status bar + landing now show the active entry's name/model
  (`provider_label` → String, `config.active_model()`).
- `Modal::ProviderAdd(Box<...>)` — boxed for the same `large_enum_variant`
  reason as `McpAdd`.

Numbers: tests 277 → **287** (providers rows/quick-add/wizard validation +
config compat/active_model), clippy **0**. New code: ~820 lines across 4
files + wiring.
