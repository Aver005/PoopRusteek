# 2026-07-08 — History recall no longer trapped by the command autocomplete

**Report (RU):** browsing sent-message history, when a recalled entry is a
`/command` the suggestion popup opens and further scrolling is blocked until you
press SPACE to dismiss it.

## ROOT CAUSE — two conflations

1. **The interceptor stole the recall keys.** `autocomplete_intercepts`
   (`src/app/keys/autocomplete.rs`) matched `KeyCode::Up`/`Down` **without
   checking modifiers**, so once a popup was open it swallowed the very
   **Ctrl+Up/Ctrl+Down** used for history recall (history moved to Ctrl+arrows
   deliberately — see `chat.rs` comment). SPACE "fixed" it only because
   inserting whitespace after the command made `refresh_autocomplete` hide the
   menu.
2. **Recall was treated like typing.** `handle_chat_key` unconditionally calls
   `refresh_autocomplete()` at the end, which opens the command menu for any
   buffer that is `/word` with no space — including a buffer *populated by
   history recall*, not composed by the user.

## FIX (ideas 1 + 2, both applied)

- **`autocomplete_intercepts`**: early-return `false` when the key carries
  `CONTROL | ALT`. The dropdown now owns only *bare* Tab/Up/Down/Enter; any
  modified nav (notably Ctrl+Up/Down) falls through to the chat handler.
- **`handle_chat_key` history arms**: after `history_prev()`/`history_next()`,
  reset `self.state.autocomplete = AutocompleteState::default()` and
  `return Ok(false)` early — skipping the trailing `refresh_autocomplete()`.
  Browsing history never pops the menu; it reopens only when the user actually
  edits (insert/backspace/delete still hit the trailing refresh). Same fix
  incidentally covers pasting a bare command.

Either change alone unblocks scrolling; together they also kill the spurious
popup flashing during recall.
