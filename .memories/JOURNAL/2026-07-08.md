# 2026-07-08 — History recall no longer trapped by the command autocomplete

**Report (RU):** browsing sent-message history, when a recalled entry is a
`/command` the suggestion popup opens and further scrolling is blocked until you
press SPACE to dismiss it.

## ROOT CAUSE — two conflations

1. **The interceptor stole the recall keys.** `autocomplete_intercepts`
   (`src/app/keys/autocomplete.rs`) matched `KeyCode::Up`/`Down` **without
   checking modifiers**, so once a popup was open it swallowed the very
   **Ctrl+Up/Ctrl+Down** used for history recall (history moved to Ctrl+arrows
   deliberately — see `chat.rs` comment). SPACE "fixed" it only because
   inserting whitespace after the command made `refresh_autocomplete` hide the
   menu.
2. **Recall was treated like typing.** `handle_chat_key` unconditionally calls
   `refresh_autocomplete()` at the end, which opens the command menu for any
   buffer that is `/word` with no space — including a buffer *populated by
   history recall*, not composed by the user.

## FIX (ideas 1 + 2, both applied)

- **`autocomplete_intercepts`**: early-return `false` when the key carries
  `CONTROL | ALT`. The dropdown now owns only *bare* Tab/Up/Down/Enter; any
  modified nav (notably Ctrl+Up/Down) falls through to the chat handler.
- **`handle_chat_key` history arms**: after `history_prev()`/`history_next()`,
  reset `self.state.autocomplete = AutocompleteState::default()` and
  `return Ok(false)` early — skipping the trailing `refresh_autocomplete()`.
  Browsing history never pops the menu; it reopens only when the user actually
  edits (insert/backspace/delete still hit the trailing refresh). Same fix
  incidentally covers pasting a bare command.

Either change alone unblocks scrolling; together they also kill the spurious
popup flashing during recall.

## VERIFICATION

`cargo build` ✅ and `cargo clippy` ✅ (both full-typecheck the crate with the
change). **Test binary could not be compiled** — host hit the documented
Windows pagefile flake (`os error 1455` / `STATUS_STACK_BUFFER_OVERRUN`,
`memory allocation … failed`) across 5 retries; not a code error. Re-run
`cargo test --bin pooprusteek -j 1` when memory frees up.

## NOTES

- No new tests: the change lives in the `App` key-dispatch layer
  (`autocomplete_intercepts` / `handle_chat_key`), which needs a live `App` and
  isn't unit-tested today. The pure recall logic (`InputState::history_*`) is
  already covered in `input.rs`.

# 2026-07-08 (session 2) — Paste & selection in the transcript; bracketed paste + paste chips

**Report (RU):** "проблемы со вставкой и выделением текста в истории сообщений";
follow-up: "вставка рванно всё вставляет, триггерит отправку если там были
переносы… а раньше было `[Pasted lines…]`".

## ROOT CAUSE
`tui::init` enabled `EnableMouseCapture` (commit `b5d26c2`, wheel-scroll) which
disables the terminal's native mouse selection (now needs Shift). Separately,
bracketed paste was **never** enabled, so a multi-line paste arrived as a stream
of `Char`/`Enter` key events — the first embedded `\n` fired an early submit.
There was no `[Pasted …]` placeholder in this codebase (`git log -S` confirms) —
the user was recalling that UX from another agent.

## FIX (user chose "bracketed paste only" — mouse capture stays for the wheel)
- **`tui::init`** now emits `EnableBracketedPaste` (`restore` →
  `DisableBracketedPaste`). Both are DECSET modes, independent of alt-screen,
  so they survive the in-loop redraw like mouse capture does.
- **New `AppEvent::Paste(String)`** routed from the `run_loop` `Event::Paste`
  arm through `handle_event` to **`keys/paste.rs::handle_paste`** (sync, no I/O).
  It mirrors `handle_key`'s dispatch precedence (onboarding → modal → view) so
  **every** text surface still receives paste (bracketed paste replaces the old
  per-char delivery, so an unrouted surface would silently lose paste). Single-
  line fields (names, URLs, token, fuzzy filter, provider/theme wizard steps)
  drop `\n`; multi-line surfaces (chat prompt, `/mcp add` JSON box, wizard
  "extra") keep it. `\r` is always stripped.
- **`InputState::insert_str`** — whole-chunk insert (char-count cursor advance),
  the shared primitive for paste.
- **Paste chips (chat only):** a multi-line chat paste collapses to a
  `[Pasted #N, L lines]` chip via `InputState::insert_paste`; the real text is
  stored in `InputState.pastes` and restored by `InputState::expanded()` at
  submit (`chat.rs::submit_input`). Chips are cleared with the buffer
  (`clear_buffer`) and on history recall. The MCP JSON box deliberately keeps
  raw text (it's parsed), so chips are NOT applied there.

## VERIFY
`cargo build` clean · `cargo test --bin pooprusteek` 423 ok (incl. 8 new
`insert_str`/`insert_paste`/`expanded` tests) · clippy `-D warnings` clean ·
`cargo fmt --check` clean. Not yet driven in a real TTY — bracketed-paste
delivery and chip rendering depend on the terminal honoring DECSET 2004.
