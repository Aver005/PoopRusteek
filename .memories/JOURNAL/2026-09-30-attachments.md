# 2026-09-30 — PDF и картинки во вложениях, перетаскивание файлов

Просьба владельца: сначала научить существующие способы (`/attach`, `@`)
прикладывать PDF и картинки, потом — перетаскивание мышью. В сообщении
показывать только имена, модели отдавать полный путь, больше пяти файлов —
счётчиком.

## Этап А — двоичные вложения

- **Клиент загрузки был сломан и ни разу не запускался**: PoW решался для
  `chat/completion` (подпись включает путь — `pow_target_path(url)` теперь
  выводит его из адреса), общий `Content-Type: application/json` затирал
  границу multipart (400 «Invalid boundary»), тип ответа падал на дробных
  `inserted_at` и `model_kind: VISION`. Типы урезаны до читаемых полей.
- `deepseek/attachments.rs`: загрузка → опрос `fetch_files` до `SUCCESS`,
  кеш id (канонический путь + размер + mtime) общий для форков, id из кеша
  перепроверяется, опрос терпит 3 сбоя подряд, `error_code` бывает **числом**
  (`40000` на битый PDF — снято вживую). «Пульс» пустым куском держит таймер
  простоя потока 120 с, пока идут PoW, загрузка и разбор.
- Прикладываются **только вложения хвоста** (`prompt::tail`). Пересылка
  истории в новую сессию старые файлы не грузит, а помечает у сообщения
  (`lost_attachments_note`). Неудачный файл — `### NOTE` модели, а не упавший
  ход: иначе сообщение с плохим файлом оставалось в хвосте и валило каждую
  отправку (нашли ревьюеры).
- `LLMProvider::accepts_attachment(&Path)`: DeepSeek берёт типы из `accept`
  веб-клиента (`UPLOADABLE`: документы, картинки, текст не в UTF-8); остальные
  провайдеры — нет, модель получает путь.
- `app/attachments.rs` — один путь для всех способов: `resolve` (от рабочей
  папки, без `./`), `util::looks_like_text` (8 КБ, UTF-16 только по BOM) и
  `util::read_text`, `user_message(text, typed, files, named, accepts)`.
  Текст — в рамке `[file name]: <полный путь>`. Чат — имена, > 5 — «N files».
- Попутно: `@src/main.rs` не разворачивался (заменялось `@main.rs`), хвост
  `:10-20` оставался в тексте; двоичный `@report.pdf` молча оставался словом;
  автодополнение `@` смотрело в папку запуска, а не в рабочую; файлы без
  текста нельзя было отправить.
- Харнесс: `exec --attach <файл>` (повторяемый), к первой реплике; неверный
  путь — `SetupFailed`.

### Проверено вживую (токен владельца)

- PDF + PNG одной репликой: коды из обоих названы, полный путь назван; PDF —
  32 токена, картинка — 205.
- Без вложения модель честно говорит, что файла нет; `--resume` помнит PDF без
  повторной загрузки.
- Экспертный режим: API принял вложение (UI его запрещает с 2026-05-14).
- Битый PDF: отказ `40000` с первого опроса, ход не падает, модель сообщает;
  `.zip` — только путь.

## Этап Б — перетаскивание

- `app/dropped_paths.rs`: вставка — перетаскивание, только если каждый кусок —
  существующий абсолютный файл (двойные/одинарные кавычки — только в начале
  куска, иначе `C:\O'Neil\a.pdf` ломался; `\ ` вне Windows; `file://` с
  процент-декодированием; больше 100 путей — это уже текст).
- `InputState::insert_files` → чипы `[📎 имя]`; больше пяти **на сообщение** —
  один `[📎 N files]`, и вторая порция сливает уже стоящие чипы; одноимённые —
  `#2`. Курсор проходит чип одним шагом, ввод внутрь чипа невозможен,
  выделение и Backspace/Delete берут чип целиком (и `[Pasted #N]`). Листание
  истории откладывает чипы черновика и возвращает их.
- Отправка: файлы чипов → вложения; команде и цели чип отдаётся путём в
  кавычках (`/attach x [📎 a.pdf]` работает); сводка «📎 …» называет только
  файлы из `/attach` и `@`, не видные в тексте. Пустой ввод не пишется в историю.
- Текст встраивается, только если он ≤ 1 МБ (`attachments::inline_text`),
  иначе — вложением или путём: меньше чтения на главном цикле.

### Windows: вставка приходит нажатиями

`crossterm 0.29` не умеет bracketed paste в WinAPI-режиме
(`EnableBracketedPaste` → «not implemented in the legacy Windows API»,
проверено по исходнику): вставка и перетаскивание приходят нажатиями, Enter
внутри отправлял сообщение. Первая версия склейки («вся пачка или ничего»,
окно 5 мс) ревью не прошла: движение мыши или Esc посреди вставки раздавали
её обратно нажатиями, короткий последний кусок с Enter отправлял. Итог
(`app/paste_burst.rs`, `gather_paste_burst`):
- каждая серия ≥ 8 текстовых нажатий — своя вставка, прочие события идут по
  порядку, движение мыши/фокус/отпускания внутри серии её не рвут;
- окно 25 мс отсчитывается **только от текстовых нажатий**, сбор не дольше
  500 мс; после вставки 100 мс её короткий хвост (`}` и Enter) — тоже вставка;
- Enter с любым модификатором внутри серии — перевод строки.

**Вживую в терминале не проверено** — харнесс ввод в TUI не умеет. Чек-лист
ручной проверки — в отчёте владельцу и ниже.

1. Ctrl+V и Shift+Insert многострочного текста: один чип, без отправки.
2. Текст, кончающийся коротким `}` и переводом строки.
3. Вставка ~50 КБ во время `cargo build`.
4. Двигать мышью во время вставки.
5. Перетащить из Проводника один файл, несколько, путь с пробелом.
6. Быстрый набор с Enter и зажатая клавиша: чипов быть не должно.
7. Вставка токена на экране входа и в поле ключа `/providers`.
8. Esc посреди большой вставки.

## Ревью

Два круга по три агента на каждый этап плюс проверка исправлений. Нашли, среди
прочего: вечную блокировку беседы отвергнутым файлом, таймер простоя 120 с,
рвавший долгий разбор, повторную загрузку всех старых файлов при сбросе
сессии, числовой `error_code`, потерю файла при правке внутри чипа.
