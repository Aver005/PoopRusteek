# 2026-07-04 — `/rate` per-minute cap + `/debug` runtime toggle

Two small, self-contained feature additions; no architectural changes.

## `/rate`: max requests/minute alongside ms interval

Previously `rate_limit_ms` was the only knob — a fixed minimum spacing
between requests. Added `agent.rate_limit_per_minute: u32`
(`#[serde(default)]` so existing `config.toml` files without the key still
parse) and a sliding-60s-window limiter in `DeepseekProvider`
(`request_history: Mutex<VecDeque<Instant>>`, pruned + capacity-checked in
`enforce_rate_limit`, `deepseek/http.rs`). Both gates are independent and
composable — either can be 0 to disable, both may be active at once.

`DeepseekProvider::new` gained a 4th positional param
(`rate_limit_per_minute`); all 5 call sites updated (`main.rs`, `app/mod.rs`,
`app/keys.rs` ×2 — provider hot-reload + onboarding, `deepseek/mod.rs` test
helper).

`/rate` syntax: `/rate <ms>` (unchanged), `/rate <N>/min` or `<N>rpm` (new,
sets the per-minute cap only), `/rate off` (zeroes both). Still returns
`CommandResult::ResetProvider` after saving config.

## `/debug [on|off]`: runtime-toggleable debug logging

Previously `debug_log` was `--debug-log`-CLI-flag-only: `init()` decided once
at startup whether to open `.dev/debug.log`, stored as `OnceLock<Option<DebugLogger>>`
— no way to flip it later. Redesigned around an `AtomicBool` gate
(`ENABLED`) plus a lazily-created `OnceLock<DebugLogger>` (`logger()`,
opens the file on first enable, reused across toggles so re-enabling never
truncates). New `set_enabled(bool)` / `is_enabled()` public API; `init()` is
now just `set_enabled(enabled)` called once at startup, so the CLI flag and
the new command share one code path.

`/debug` (new file `commands/defs/debug.rs`) parses `on`/`off`/empty (flips
current state via `is_enabled()`), pushes a system message confirming the new
state, returns `CommandResult::Handled` — no provider reset needed.

## Follow-up: user-reported bugs from testing the above

1. **`/rate 20` / `/rate 20/min` looked like a no-op.** The command *did*
   save config and return `CommandResult::ResetProvider`, but that variant's
   handler (`app/keys.rs` around `CommandResult::ResetProvider`) only
   reloads config + rebuilds the provider — it never pushes a chat message,
   unlike e.g. `/reset`. So the setting was actually applied but silently.
   Fixed by having `RateCommand::execute` push a system message on both the
   bare `/rate` (shows current settings + usage, was previously just a bare
   usage error) and after a successful change ("Rate limit updated: …").
   Added `AgentConfig::rate_limit_display()` (`config/mod.rs`) as the single
   formatter both the command and the stats panel share — `"off"` /
   `"500ms"` / `"10/min"` / `"500ms, 10/min"`. 4 new unit tests.
2. **Up-arrow after submitting showed a stale previous-run entry, not what
   was just typed.** `append_history()` (`session.rs`) only ever wrote to
   `history.json` on disk; `InputState.history` (the in-memory Vec that
   `history_prev`/`history_next` actually browse) was loaded once at
   `App::new` and never updated again during the session. Fixed by
   reassigning `self.state.input.history = crate::session::load_history()`
   right after `append_history(&input)` in `app/keys.rs` — keeps the recall
   list a straight mirror of disk state instead of letting the two diverge.

## Bug: PowerShell empty-output false positive

User reported that a PowerShell command with legitimately empty output (e.g.
`Get-ChildItem -Filter *.go` in a Rust repo — no matches) came back to the
agent as `[powershell exited successfully but returned no stdout/stderr;
output capture likely failed]`, a `ToolResult::error`. That branch
(`tools/shell.rs`, added 2026-07-03 evening alongside unrelated SSE debugging
work) was a speculative guard against a suspected-but-never-confirmed
capture bug — exit 0 + empty stdout/stderr is just as often a normal,
silent-success outcome (no matches, `Set-Content`, etc.). Flagging it as an
error made the agent believe a healthy command had failed.

Fixed: same branch now returns `ToolResult::success("(command completed
successfully with no output)")` instead of an error. The
`shell.foreground.empty_success` debug-log event stays in place — if a real
capture bug shows up later, the log will still have it.
