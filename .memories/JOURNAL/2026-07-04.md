# 2026-07-04 — `/rate` per-minute cap + `/debug` runtime toggle

Two small, self-contained feature additions; no architectural changes.

## `/rate`: max requests/minute alongside ms interval

Previously `rate_limit_ms` was the only knob — a fixed minimum spacing
between requests. Added `agent.rate_limit_per_minute: u32`
(`#[serde(default)]` so existing `config.toml` files without the key still
parse) and a sliding-60s-window limiter in `DeepseekProvider`
(`request_history: Mutex<VecDeque<Instant>>`, pruned + capacity-checked in
`enforce_rate_limit`, `deepseek/http.rs`). Both gates are independent and
composable — either can be 0 to disable, both may be active at once.

`DeepseekProvider::new` gained a 4th positional param
(`rate_limit_per_minute`); all 5 call sites updated (`main.rs`, `app/mod.rs`,
`app/keys.rs` ×2 — provider hot-reload + onboarding, `deepseek/mod.rs` test
helper).

`/rate` syntax: `/rate <ms>` (unchanged), `/rate <N>/min` or `<N>rpm` (new,
sets the per-minute cap only), `/rate off` (zeroes both). Still returns
`CommandResult::ResetProvider` after saving config.

## `/debug [on|off]`: runtime-toggleable debug logging

Previously `debug_log` was `--debug-log`-CLI-flag-only: `init()` decided once
at startup whether to open `.dev/debug.log`, stored as `OnceLock<Option<DebugLogger>>`
— no way to flip it later. Redesigned around an `AtomicBool` gate
(`ENABLED`) plus a lazily-created `OnceLock<DebugLogger>` (`logger()`,
opens the file on first enable, reused across toggles so re-enabling never
truncates). New `set_enabled(bool)` / `is_enabled()` public API; `init()` is
now just `set_enabled(enabled)` called once at startup, so the CLI flag and
the new command share one code path.

`/debug` (new file `commands/defs/debug.rs`) parses `on`/`off`/empty (flips
current state via `is_enabled()`), pushes a system message confirming the new
state, returns `CommandResult::Handled` — no provider reset needed.

## Follow-up: user-reported bugs from testing the above

1. **`/rate 20` / `/rate 20/min` looked like a no-op.** The command *did*
   save config and return `CommandResult::ResetProvider`, but that variant's
   handler (`app/keys.rs` around `CommandResult::ResetProvider`) only
   reloads config + rebuilds the provider — it never pushes a chat message,
   unlike e.g. `/reset`. So the setting was actually applied but silently.
   Fixed by having `RateCommand::execute` push a system message on both the
   bare `/rate` (shows current settings + usage, was previously just a bare
   usage error) and after a successful change ("Rate limit updated: …").
   Added `AgentConfig::rate_limit_display()` (`config/mod.rs`) as the single
   formatter both the command and the stats panel share — `"off"` /
   `"500ms"` / `"10/min"` / `"500ms, 10/min"`. 4 new unit tests.
2. **Up-arrow after submitting showed a stale previous-run entry, not what
   was just typed.** `append_history()` (`session.rs`) only ever wrote to
   `history.json` on disk; `InputState.history` (the in-memory Vec that
   `history_prev`/`history_next` actually browse) was loaded once at
   `App::new` and never updated again during the session. Fixed by
   reassigning `self.state.input.history = crate::session::load_history()`
   right after `append_history(&input)` in `app/keys.rs` — keeps the recall
   list a straight mirror of disk state instead of letting the two diverge.

## Bug: PowerShell empty-output false positive

User reported that a PowerShell command with legitimately empty output (e.g.
`Get-ChildItem -Filter *.go` in a Rust repo — no matches) came back to the
agent as `[powershell exited successfully but returned no stdout/stderr;
output capture likely failed]`, a `ToolResult::error`. That branch
(`tools/shell.rs`, added 2026-07-03 evening alongside unrelated SSE debugging
work) was a speculative guard against a suspected-but-never-confirmed
capture bug — exit 0 + empty stdout/stderr is just as often a normal,
silent-success outcome (no matches, `Set-Content`, etc.). Flagging it as an
error made the agent believe a healthy command had failed.

Fixed: same branch now returns `ToolResult::success("(command completed
successfully with no output)")` instead of an error. The
`shell.foreground.empty_success` debug-log event stays in place — if a real
capture bug shows up later, the log will still have it.

## Bug: multi-line system messages rendered as one glued line

The `/rate` fix above used `"...\n\n..."` in a system message and it showed
as one run-on line. Root cause: `Role::System` in `render_chat`
(`tui/widgets/chat.rs`) put the whole message content into a single `Span`
inside a single `Line` — a `Span`'s text is one terminal row, so embedded
`\n`s don't create new rows, ratatui just prints past them. `Role::User`/
`Role::Tool` already split on `.lines()` into one `Line` per row; `Role::System`
never did. Fixed to match: split `visible_content().lines()`, icon (`ℹ`) on
the first line, 3-space indent on continuation lines.

## Feature/bugfix: remote session resume on `/load` (this session)

User-reported bug: loading an existing local session via `/sessions` →
`/load` and sending a message created a **new DeepSeek remote session**,
even though the old remote session was still alive — with no indication
anything had changed.

**Root cause**: DeepSeek's server-side `SessionState` (`session_id` +
`parent_message_id`, `provider/deepseek/session.rs`) was purely in-memory —
never written to the local `Session` file. `handle_load_session` also called
`provider.reset()` unconditionally on every local load, clearing whatever
in-memory identity happened to exist. So *any* restart or `/load` always
silently started a fresh remote `chat_session`; the local `Session.id` was
never the same identifier as DeepSeek's `chat_session.id` to begin with.

**Design** (full detail in `reference/CONFIG.md` → "Remote session resume"):
- `Session` gained `provider_session_id: Option<String>`,
  `provider_parent_message_id: Option<i64>`, `broken: bool` (all
  `#[serde(default)]` — old session files without them still load).
  `save_session`'s tag-only last param became `meta: &SessionMeta` (a small
  struct bundling `tag`/`broken`/the two provider fields) so the function
  signature doesn't grow every time one more persisted field is added;
  `save_session_with_tag` folded into it. `SessionSummary` gained `broken`
  for the `/sessions` list.
- `LLMProvider` gained `session_identity()` (sync, in-memory), `async
  session_is_alive(id)` (delegates to the existing `fetch_remote_history` —
  any error reads as "not alive"), `async adopt_session(id, parent_msg_id)`
  (sets `SessionState` directly with `system_sent_for_session: true`,
  skipping `chat_session/create`). All default to no-ops/`false`/`None` so
  only DeepSeek needed a real implementation.
- `Conversation` gained `tag`/`broken` fields mirroring the on-disk
  `Session` — needed because `auto_save_session` only ever writes what's on
  the live conversation, never reads-before-writing the file. This also
  fixed a **pre-existing latent bug**: every auto-save after a `/load` or
  `/import` silently wiped the session file's `tag` back to `None`, because
  `auto_save_session` always passed `tag: None` downstream. Now `import.rs`
  and `handle_load_session` set `conv.tag`/`conv.broken` from the loaded
  data, and `auto_save_session` round-trips them.
- `handle_load_session`: if the loaded session has a `provider_session_id`,
  spawns `session_is_alive` off the event loop (new `AppEvent::
  SessionAvailabilityChecked`, same non-blocking pattern as the existing
  `SessionFetched`) and reacts in `apply_session_availability`: alive →
  `adopt_session` (silent, continues the thread); dead →
  `provider.reset()` + `finalize_broken_session` (persists `broken: true`
  with the remote pointer cleared, mirrors it on `Conversation`, pushes a
  system message). No known remote id → just `reset()` (unchanged default
  first-run behavior). Once reset, the **existing** first-turn `build_prompt`
  logic (nothing new needed here) replays full local history as one
  flattened prompt on the next message, satisfying "recreate globally
  and locally with the full history sent as one prompt" for free.
- `broken` isn't a permanent scar: `auto_save_session` clears it back to
  `false` the moment `provider.session_identity()` reports a live identity
  again (proof a turn just completed successfully on a new remote session).
- `/sessions` (`session_list.rs`) shows broken entries with a ⚠ prefix and
  yellow text — new `PickerItem::warn(bool)` builder, read by
  `render_picker` (`tui/render.rs`) to pick `theme.warning` over
  `theme.text_soft`.

**Known gap** (documented, not fixed): the separate "remote-id-not-found-
locally" import path (`apply_fetched_session`) doesn't attempt resume either
— `fetch_remote_history`'s `chat/history` parsing never extracts a message
id, so there's no `parent_message_id` to adopt safely. Left on default
fresh-session behavior rather than guess the wire format.

Numbers: tests 223 → **227** (3 new `DeepseekProvider` tests for
`session_identity`/`adopt_session`, 1 new `session.rs` round-trip test).
Clippy: 0 warnings throughout.

## Feature: MCP OAuth authorization (`/mcp auth` / `/mcp oauth`)

Previously an HTTP/SSE MCP server answering 401 just sat in
`MCPServerStatus::Error(...)` forever — no way to authenticate. Added a full
OAuth 2.1 authorization-code + PKCE flow (RFC 9728 protected-resource
discovery, RFC 8414 AS metadata, RFC 7591 dynamic client registration),
triggered by `/mcp auth` (alias `/mcp oauth`).

**New dependencies**: `keyring = "4"` (default `v1` feature — Windows
Credential Manager / macOS Keychain / Linux Secret Service), `open = "5"`
(browser launch), `sha2 = "0.10"` (PKCE S256). Also enabled reqwest's
`"form"` feature (needed for `.form()` — wasn't on before). No `rand`
dependency: PKCE `code_verifier`/CSRF `state` are generated from
concatenated `uuid::Uuid::new_v4()` bytes, base64url-encoded.

**Token storage decision**: OS keyring, not a hand-rolled cipher — confirmed
with the user explicitly. This is also the *first* encrypted-at-rest secret
storage in the repo; the DeepSeek token in `config.toml` is still plaintext
(unchanged, out of scope here) — see `reference/CONFIG.md`.

**New files**: `mcp/oauth.rs` (discovery, dynamic client registration, PKCE,
local-loopback callback listener via raw `TcpListener` + hand-parsed
`GET /callback?...` line, token exchange/refresh — no new HTTP-server
dependency), `mcp/oauth_store.rs` (keyring-backed `save`/`load`/
`with_bearer_header`, all keyring calls on `spawn_blocking` since the crate's
API is synchronous).

**Wiring** (deliberately minimal new surface — see `reference/MCP.md`
"AUTHORIZATION" section for full detail):
- `MCPServerStatus::AuthRequired(Option<String>)` (the hint = `resource_metadata`
  URL parsed from `WWW-Authenticate`, if the server sent one).
  `AppError::McpAuthRequired { www_authenticate }` is the signal transports
  raise; `transport.rs` checks for 401 in both `HttpTransport` and
  `SseTransport` (unified into shared `apply_common_headers`/
  `auth_required_error`/`capture_session_id` free functions — the two
  transports had already been duplicating header-attach/session-capture
  logic across 4 methods, so this pass fixed a pre-existing wart while
  adding the 401 check rather than duplicating that too).
- `build_client` (manager.rs) is now the **only** place any transport client
  gets constructed — `add_server` used to duplicate its `Http`/`Sse` arms
  verbatim; unified so the new `oauth_store::with_bearer_header` injection
  (merges a stored `Authorization: Bearer` into the config's headers,
  best-effort no-op if nothing's stored) covers every call site
  (initial connect, `toggle_server`, `reconnect_server`) for free. **No new
  reconnect method** — after a completed OAuth flow, the existing
  `reconnect_server` is just called again.
- `McpViewState.auth_mode: bool` + `visible_indices()` (identity outside
  auth mode, filtered to `needs_auth` inside it). Deliberately *not* filtering
  `servers` itself in place — it's kept in sync by the throttled
  `McpStatus::update_stats` poll (`app/mcp_status.rs`) on a 2s cadence, which
  would silently undo any in-place filtering.
- `keys.rs`: new `handle_mcp_auth_key` (separate from `handle_mcp_key` —
  cleaner than threading `auth_mode` conditionals through every existing
  arm); Enter spawns `oauth::run_flow` off the event loop, result comes back
  as `AppEvent::McpOAuthResult`, success path calls the existing
  `reconnect_server` and reuses `McpOperationDone` for its own outcome.
- `render.rs`: title/subtitle/footer swap on `auth_mode`, empty-list message,
  new `"auth required"` status arm (icon `⚿`, `theme.warning`, short code
  `AUTH`).

**Known limitations** (documented, not silently papered over): servers whose
authorization server has no `registration_endpoint` (no RFC 7591 support)
fail with a clear error rather than a silent no-op — manual client_id
config is a reasonable follow-up, not done here. `keyring` can fail to find
a backend on a headless Linux box with no Secret Service/D-Bus running —
`load`/`save` degrade to "never authorized", not a hard error.

Numbers: tests 227 → **242** (15 new: PKCE/RFC-8414-vs-OIDC well-known-path

### Bug found live: `keyring` 4.1.3's `Entry::new` always fails with `NoDefaultStore`

First real end-to-end run of `/mcp auth` hit
`Authorization failed: MCP error: Keyring unavailable for 'outline': No
default store has been set, so cannot search or create entries` on every
attempt. Traced into `keyring-4.1.3/src/v1.rs`: `Entry::new` only calls its
internal `set_credential_store()` when
`SET_CREDENTIAL_STORE.compare_exchange(false, true, ..) == Ok(true)` — but
`AtomicBool::compare_exchange`'s `Ok` branch carries the *value before the
swap*, so a successful CAS starting from `false` always yields `Ok(false)`,
never `Ok(true)`. Confirmed with a throwaway `rustc` one-liner. That
`if`-condition is therefore always false: no platform credential store is
ever registered, `keyring_core::Entry::new` always errors
`NoDefaultStore`, and because the `AtomicBool` still flips to `true` as a
side effect of the (failed-comparison) CAS, no later call can retry the init
either — it's broken for the lifetime of the process, on every platform,
not a Windows-specific or transient issue.

**Fix**: `oauth_store.rs::ensure_default_store()` — a `std::sync::Once`-gated
function that does the exact same init `keyring`'s own (buggy) internal
`set_credential_store()` was supposed to do, calling
`keyring_core::set_default_store(...)` directly with the right
per-target native store (`windows-native-keyring-store` /
`apple-native-keyring-store::keychain` /
`zbus-secret-service-keyring-store`), called from `entry()` before every
`keyring::Entry::new`. Added `keyring-core` plus the 3 target-gated store
crates as **direct** dependencies in `Cargo.toml` (mirroring keyring's own
`v1` feature's `[target...]` tables exactly) — since these are the exact
same crates/versions keyring's `v1` feature already compiles in
transitively, this adds no new dependency edges, just names them so our
code can call the setter. If upstream ships a fix, this workaround (and the
3 extra direct deps) can be dropped — see `reference/MCP.md` AUTHORIZATION
GOTCHAS for the full citation.

Verified fixed: clean rebuild, 242/242 tests, clippy 0 warnings.

## Feature: `/mcp add` — convenient new-server onboarding

User asked for a convenient way to add new MCP servers directly through
`/mcp`, and specified the exact shape: `/mcp add` (no args) offers a choice
between "paste JSON" and "step-by-step wizard"; `/mcp add <args>` tries a
quick inline add and falls back to the same choice on any parse failure.

**Manager**: `MCPManager::add_new_server(name, config) -> AppResult<MCPServerStatus>`
(`manager.rs`) — rejects a duplicate name, otherwise reuses the already-private
`add_server`/`connect_server`/`persist_config` (same `impl` block, no
visibility changes needed) to add as `ServerSource::Own`, connect
immediately, and persist. Also added `has_server(name) -> bool` for the
wizard's live duplicate-name check.

**New module `app/mcp_add.rs`** — deliberately pure (no crossterm/ratatui
dependency), fully unit-tested: `McpAddState` (`ChooseMethod` /
`PasteJson { input: InputState, error }` / `Wizard(Box<WizardState>)` — boxed
per clippy `large_enum_variant`, a `WizardState`'s 3 `InputState` fields make
it ~376 bytes vs. the other variants' <40), `WizardState.step` walking
`Name → Transport → Primary → Extra → Confirm`, and the parsers:
`parse_pasted_json` (accepts the Claude-Desktop-style `{"mcpServers": {...}}`
wrapper for multi-server pastes, or a bare object with a bolted-on `"name"`
field), `parse_quick_add` (delegates to the JSON parser if the arg looks like
`{...}`, else `<name> <command> [args...]` stdio shorthand),
`split_command_line` (whitespace-only, no quoting), `parse_env_lines`
(`KEY=VALUE`) / `parse_header_lines` (`Name: value`).

**UI wiring**: new `Modal::McpAdd` variant; reused `app::input::InputState`
(the main chat input's editing state) for every free-text step instead of
inventing a new text-field type — added `Clone` to it (previously only
`Debug + Default`) since `Modal` is cloned wholesale in `handle_key` before
matching. `keys.rs::apply_text_key` is a small shared free function applying
the common editing keys (insert/backspace/delete/cursor movement,
Shift+Enter for newline where allowed) so each wizard step's own handler only
adds its Enter/Esc transition — mirrors the main chat input's own
Shift+Enter-for-newline convention rather than inventing a new one.
`handle_mcp_add_key` (new method) drives the whole state machine; validates
on Enter before advancing a step (empty/duplicate name, bad command line,
invalid URL via `reqwest::Url::parse`, malformed env/header lines) with
inline errors rather than silently rejecting. `render_mcp_add` (+ shared
`push_text_box_lines`, converting an `InputState`'s char-index cursor into
(row, col) by walking the buffer once) draws all three top-level states.

Quick-add's fallback-on-parse-failure pushes an explanatory system message
before opening the choice modal — a silent fallback (per the letter of the
request) would leave the user unsure why their command didn't do what they
expected; this satisfies the spec while staying debuggable.

Full design detail: `reference/MCP.md` ADDING SERVERS section.
