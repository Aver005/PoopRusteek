# 2026-09-30 — скиллы «как файлы» и досылка изменённого промпта

Вопрос владельца: не лучше ли прикреплять скиллы к сообщению DeepSeek как
`.md`-файлы вместо текста в системном промпте — «PDF на много страниц
прикрепить можно, а столько же текста вставить нельзя, значит, файлы
оптимизированы».

## Замер (веб-чат, клиент 2.5.0, Chrome DevTools + `exec`)

- Загрузка: PoW с `target_path=/api/v0/file/upload_file` → multipart
  `file/upload_file` (ответ `status: PENDING`) → опрос `file/fetch_files` до
  `SUCCESS`, там `token_usage` → в `chat/completion` поле `ref_file_ids`.
  К сессии загрузка не привязана.
- Токены: `.md` 286 байт = 80 токенов, и они входят в
  `accumulated_token_usage` (289 на ответ). Файл 2,4 МБ (метки на 1/50/99 %):
  вложением — 407 114, тем же текстом в `prompt` через `--system-append` —
  411 732 (разница ≈ наш системный промпт 4,6K). Все три метки найдены обоими
  способами; «последний Record» оба раза назван неверно — внимание, не обрезка.
- `prompt` принимает 2,4 МБ. Интерфейс сам превращает длинную вставку в
  `.txt`-вложение («Вставить оригинал») — отсюда впечатление, что файлом влезает
  больше. Независимый замер (lavabyte/deepseek-web-api, 2026-09-13): потолок
  текста ~800–830K токенов, дальше `Length limit reached`.
- Модель процитировала, как видит вложение: `[file name]: commit-style.md` /
  `[file content begin]` / … / `[file content end]` — как в README DeepSeek-R1.
- Экспертный режим не принимает файлы с 2026-05-14 («资源紧张，不支持文件上传»,
  ITHome). 1M контекста во всех официальных сервисах с 2026-04-24 (новость V4).

Вывод: выгоды у загрузки нет, только PoW, опрос и скрытый счёт токенов. Рамку
ставим сами.

## Что сделано

- `provider::prompt::attached_file` — рамка вложения; `SkillDefinition::
  as_attached_file` оборачивает скилл как `<slug>.md` в системном промпте
  (полный режим, с вводной строкой «следуй скиллу…») и в ответе `skill load`.
- `SessionState::plan_system_delivery` → `SystemDelivery::{Fresh, Held,
  Changed(FileChanges)}`. Раньше промпт уходил раз за сессию, и скилл,
  включённый посреди беседы, до модели не доходил. Теперь изменённый промпт
  досылается целиком под `### SYSTEM PROMPT UPDATE`; доставленным считается в
  `mark_session_after_success`. Подхваченная сессия досылает один раз.
- `FileChanges` сравнивает строки `[file name]:` и называет выключенные и
  подключённые файлы плюс список действующих.
- `MCPManager::get_all_tools`/`get_all_resources` отсортированы: порядок
  `HashMap` после переподключения давал бы ложные досылки.

## Проверки

- A/B рамки (8+8 `exec`, скилл с 4 проверяемыми правилами, без упоминания в
  запросе): `## Skill:` — 8/8, файловая рамка — 8/8. Регрессии нет; выигрыш
  этим не показан — задача упирается в потолок. Оценщик проверен на провале.
- Досылка: ход без скилла (`Fresh`, 17 022 симв.) → `--resume` со скиллом:
  `Changed` (17 912, с `ZEBRA-7731`, без `LOCAL MEMORY`), модель следует; вторая
  реплика `Held` (405) — модель следует без повторной пересылки.
- Выключение: общая шапка «заменяет целиком» — 0/1 (модель держалась прежнего
  стиля из истории). С поимённым списком — симуляция 1/1, реальный механизм на
  подхваченной сессии 2/3. Надёжно — только новая сессия.
- `fmt`, `clippy -D warnings` (как в CI), 721 тест затронутых модулей.

## Открыто

- Харнесс не умеет менять системный промпт внутри одного `exec`, поэтому путь
  «разница известна» (`held` есть) проверен модульно и одной симуляцией.
- Исследовательская гипотеза (не проверена): рамка «документа» может ослабить
  следование инструкциям у моделей, обученных против prompt injection. Нужен
  A/B на задаче без потолка.
