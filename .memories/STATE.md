Then the harness was pointed at **real developer tasks** (`sandbox/scenarios/dev/`: build a static page, fix a failing test, respect explicit constraints, explain without editing) — which needed two things the harness lacked: a fresh scratch workspace per repeat (`workspace_template`, copied per run and kept for inspection) and expectations over the **files that came out** (`files_exist`/`files_absent`/`file_matches`), because a confident answer over an empty directory is the failure that matters. Three findings followed, in ascending order of interest. (1) An empty model reply ended the turn as `status=success` — "build me three files" returned in 1.4s having created none, silently; now nudged, retried, and reported as an error if it persists. (2) The reason for those empty replies: a rate-limited request answers **HTTP 200** and sends `{"type":"error",…,"finish_reason":"rate_limit_reached"}` *inside* the stream, then closes cleanly — the parser matched no such frame, logged it as `stream.skipped`, and read the clean EOF as a normal stop. Now recognized, and rate limits wait and retry with backoff (only while no text has been emitted, so a retry cannot duplicate a partial reply). (3) The agent-quality one: given an empty directory the model ran `ls -la`, then replied *"Директория пуста… Создам три файла"* — announcing the work — and the turn ended, because a text-only reply is treated as a finished answer. **Announcing intent counts as finishing.** That one is not a code bug; it is the open question the system-prompt comparison is for.
